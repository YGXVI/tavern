# Design

## Context

Мотивация — proposal.md («Why»). Что важно для подхода:

- Интерфейс TASK-007 читает данные синхронно из одного объекта `db` (`getDB()`, `getCampaign()`), а пишет только через `commit(mutator)` / `updateCampaign()` / `updateScene()` (58 мест вызова) и шину `bus` (17 типов мгновенных событий). Экраны и стол не знают, откуда данные.
- Сайт без сборки (DEC-002), публикуется из `main` на Vercel (DEC-010), репозиторий публичный: всё в `dist/` видно любому.
- В кампании 1 мастер и до ~6 игроков; одновременных правок одного объекта мало, но мастер и игроки постоянно двигают разные токены.
- Требования — в delta specs: `campaign-access`, `table-sync`, `auth`, `campaigns`, `maps`.

## Goals / Non-Goals

**Goals:** серверный режим, в котором экраны и стол работают без переписывания; права в базе, а не в интерфейсе; песочница остаётся рабочей; откат — одним флагом.

**Non-Goals:** свой сервер или функции Vercel; сборщик; офлайн-очередь изменений (при обрыве — сообщение и перезагрузка состояния, а не отложенная отправка); серверный расчёт тумана.

## Decisions

### 1. Supabase, отдельно от DnD Kids

Отдельная организация `rasputye` и проект `tavern` (бесплатный тариф), отдельное приложение Discord «Распутье». Участников команды приглашают только в эту организацию.

Альтернативы: Firebase — нет встроенного входа через Discord и правил на уровне строк SQL; свой сервер (функции Vercel + база + WebSocket-сервис) — в разы больше кода и обслуживания; Liveblocks/PartyKit — только реальное время, без базы и прав. Supabase закрывает вход, базу, права, реальное время и файлы одним сервисом.

### 2. Клиент: два источника данных за одним `store.js`

`store.js` сохраняет текущий API (`getDB`, `commit`, `subscribe`, `bus`, `setPresence`, `onlineUsers`) и получает два режима:

- **песочница** — нынешний код без изменений поведения (`localStorage` + `BroadcastChannel`);
- **сервер** — новый модуль `dist/js/server/sync.js` загружает строки кампании, собирает из них объект кампании прежней формы (`docs/data.md`) и кладёт в `db`. Игрок получает объект без скрытых данных — их не прислал сервер.

`commit(mutator)` в серверном режиме: применить изменение к копии сразу (оптимистично, интерфейс не ждёт сети) → сравнить «до/после» по сущностям (поля кампании, участники, герои, сцены, тайное сцены, токены, рисунки, журнал, запросы) → отправить только изменённые строки → при отказе сервера вернуть сущность с сервера и показать тост «Не сохранилось: …». Сравнение — чистая функция, покрывается тестами `npm test`.

Режим выбирается на экране входа и хранится в `sessionStorage` (`rasputye-v2-mode`): `sandbox` или `server`. Новые ключи песочницы не появляются, старые не трогаются.

Альтернатива — переписать вызовы на явные запросы к серверу: 58 мест, риск сломать стол. Сравнение снимков дешевле и оставляет стол как есть.

Подключение библиотеки: `@supabase/supabase-js` 2.x ES-модулем с jsDelivr с точной версией (не моложе двух недель на момент реализации). Адрес проекта и публичный (publishable) ключ — в `dist/js/server/config.js`; служебный ключ в браузер и Git не попадает.

### 3. Схема данных

| Таблица | Содержимое | Читают | Пишут |
| --- | --- | --- | --- |
| `profiles` | ник, аватар, цвет из Discord | вошедшие (минимальный профиль) | сам пользователь; создаётся триггером при первом входе |
| `campaigns` | название, описание, обложка, уровень, места, активная сцена, настройки, пауза | участники и ожидающие | мастер |
| `combats` | бой кампании (`jsonb`: раунд, ход, очередь, потраченное движение, `current` — чей ход) | участники | мастер; игрок — триггер пропускает инициативу любого героя (если не брошена), движение любого видимого токена и конец хода, когда `current` — герой (решение 30.10 09:19: можно играть за товарища с телефона) |
| `campaign_members` | роль, статус, герой, личная сцена | участники кампании; свою строку — ожидающий | мастер; вступление — функция `join_campaign(code)`; уход — сам игрок |
| `campaign_invites` | код, срок, ручное одобрение | мастер | мастер |
| `characters` | лист героя (`jsonb`) | участники | владелец героя и мастер |
| `scenes` | карта, сетка, свет, стены, туман (режим и кисть), местность, переходы, открытые метки (`jsonb`) | участники | мастер; игрок — триггер пропускает только открыть/закрыть незапертую дверь (и «Открывание») |
| `scene_secrets` | ловушки, метки «только мастеру», неоткрытые тексты | мастер | мастер |
| `scene_explored` | исследованные клетки | участники | участники — только добавление функцией `add_explored` |
| `tokens` | токен (`jsonb`) + отдельные колонки `scene_id`, `character_id`, `hidden`, `ord` | мастер — все; игрок — нескрытые | мастер; игрок — вставка своего героя; изменения — триггер: у своего героя положение, поворот, размер, свет, аура, «Отход», сцена; у любого видимого незакреплённого токена при открытом перемещении — положение и поворот |
| `drawings` | линии и надписи | участники | автор и мастер |
| `log_entries` | броски и события: кто, когда, вид, флаг `hidden`; подпись и результат — только у открытых | участники | автор (вставка) |
| `log_secrets` | подпись, сумма и грани скрытого броска | автор и мастер | автор (вставка) |
| `save_requests` | запрос спасброска и результаты | участники | мастер; игрок — триггер пропускает новый результат любого героя, один раз |
| `portal_requests` | просьба пройти через переход | мастер и автор | автор (вставка), мастер (удаление) |

Клиент сам задаёт строковые ID (как в песочнице: `c-…`, `t-…`), поэтому ключи таблиц — `text`. Журнал на сервере не обрезается: клиент держит последние 120 записей, удаление старых записей адаптер не отправляет. Поле `doorAttempt` (попытка взлома) в серверном режиме не сохраняется — мастер получает её мгновенным событием `lockpick`, как и сейчас.

Права — политики RLS с вспомогательными функциями `is_member(campaign)`, `is_master(campaign)`, `my_character(campaign)`. Действия игрока сверх своей строки (вступление, инициатива, конец хода, результат спасброска, исследованные клетки) — функции Postgres `security definer`, которые сами проверяют условия. Миграции — в `supabase/migrations/`, применяются к проекту и хранятся в Git.

Альтернатива — вся кампания одним `jsonb`, как в песочнице: быстрее, но RLS не умеет скрывать части документа и разрешать игроку менять только свой токен.

Риск одновременной правки сцены: игрок, открывший дверь, отправляет `data` сцены целиком; если мастер в ту же секунду поменял стены или свет, последняя запись победит. Редкий случай, принимаем; остальные сущности — отдельные строки.

### 4. Реальное время

- Сохранённые данные — подписка на изменения таблиц кампании (Postgres Changes), события проверяются RLS для каждого получателя.
- Мгновенные события `bus` (перетаскивание, линейка, шаблон, пинг, бросок, чтение вслух и др.) — Broadcast на приватном канале `campaign:<id>`; «в сети» — Presence на том же канале. Доступ к каналу — политики на `realtime.messages` по членству; публичный доступ к Realtime в настройках проекта выключается.
- Скрытый бросок: адаптер сохраняет его двумя строками — открытая часть в `log_entries` (игроки видят «Скрытый бросок», как сейчас в `dice.js`) и подпись с результатом в `log_secrets`; в канал мастер отправляет только открытую часть.
- Удаления: Postgres Changes не применяет RLS к удалениям и не может отфильтровать «стало невидимым». Поэтому, когда мастер скрывает токен или удаляет объект, его клиент дополнительно отправляет в канал событие с идентификаторами (`hidden-ids`), а клиенты игроков убирают их у себя; после переподключения клиент перезагружает кампанию целиком.

### 4а. Что выполняет клиент мастера

Ловушки и тайное сцены игрок не получает, поэтому срабатывание ловушки на пути героя определяет клиент мастера: получив новое положение токена (своё или из реального времени), он проверяет клетки между старым и новым местом, как раньше `findTrapOnPath`. Если мастер не открыт за столом, ловушка не сработает — это ограничение записано в README.

### 5. Вход через Discord

`signInWithOAuth({ provider: 'discord' })` с PKCE: после Discord браузер приходит на `https://rasputye.vercel.app/?code=…` (обычный параметр адреса, не `#`, поэтому не спорит с маршрутами `#/…`), клиент обменивает код на сессию и переходит на сохранённый маршрут (`#/join/…` или `#/campaigns`). Supabase хранит почту Discord у себя в `auth.users`; приложение её не читает и не показывает. Разрешённые адреса возврата: `https://rasputye.vercel.app/**` и `http://localhost:4173/**`.

### 6. Карты

Приватный бакет `maps`, путь `<campaign_id>/<uuid>.<ext>`; читают участники, пишет мастер. В данных сцены ссылка `sb:<путь>`; `resolveSrc` получает временную подписанную ссылку и кэширует её. Встроенные карты и портреты остаются в `dist/assets`.

## Risks / Trade-offs

- [Ошибка в политике RLS откроет секреты] → набор SQL-проверок `supabase/tests/rls.sql`: от имени мастера, игрока и постороннего проверить каждый сценарий `campaign-access`; запускать после каждой миграции и перед PR.
- [Бесплатный проект засыпает после недели без игр] → экран «Сервер спит» с подсказкой, кто и где его будит; песочница работает без сервера.
- [Сравнение снимков пропустит изменение] → тесты на каждую сущность; при сомнении клиент перезагружает сущность с сервера.
- [Игрок видит стены и всех нескрытых существ в данных] → осознанное ограничение (как в Foundry), записано в proposal («Вне объёма»); для засад мастер прячет токены.
- [CDN библиотеки недоступен] → сообщение об ошибке и песочница; при повторении — положить закреплённую сборку в `dist/vendor/` отдельным решением.
- [Тест-проверки RLS требуют доступа к проекту] → в CI их нет (секретов в CI не добавляем); запускает автор через Supabase и прикладывает вывод к PR.

## Migration Plan

1. Создать организацию `rasputye` и проект `tavern`; применить миграции; выключить публичный Realtime; создать бакет `maps`.
2. Человек создаёт приложение Discord «Распутье», добавляет адрес возврата Supabase, вводит ID и секрет в панели Supabase; задаёт адреса сайта.
3. Влить PR: на сайте появляется настоящий вход, песочница — второй кнопкой.
4. Откат: `SERVER_ENABLED = false` в `dist/js/server/config.js` — сайт работает как сейчас, серверные данные не удаляются. Удаление проекта Supabase — только отдельным решением владельца.

## Open Questions

Блокирующих нет. Принятые допущения (проверяющий может оспорить):

- Аватар — ссылка на CDN Discord из данных входа (`avatar_url`), без копирования в Storage; если Discord её сменит, аватар обновится при следующем входе.
- Со-мастер вне объёма; колонка `role` в `campaign_members` позволит добавить его позже без переноса данных.
- Лимит участников — по полю «места» кампании (как в песочнице), проверяется в `join_campaign` и при одобрении заявки.
