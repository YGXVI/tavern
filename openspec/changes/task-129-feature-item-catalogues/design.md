# Design

## Context
Main `33200d87f1e13a7c4180ec33ed49a0e4cfd5278c`: data/magic-items/magic-items-2014.json содержит934 ID,221 совпадение SRD,713 metadata-only и98 вложенных SRD-вариантов. dist/js их не загружает. data/rules-2014/player-rules.json и srd-5.1.json содержат страницы, не готовые сущности способностей. Лист main хранит features/inventory строками; TASK-004 проектирует массивы features[] и inventory[], версии, идемпотентность, права владельца/мастера. Повторно этот контракт не вводим.

## Goals / Non-Goals
Первый выпуск = оба каталога в приложении, личные записи и добавление экземпляров в лист. «Способности» здесь — классовые/подклассовые и расовые особенности, черты и выбираемые варианты SRD2014; не шесть характеристик и не отдельный каталог атак монстров. Заклинания остаются существующими Spell-сущностями, способности лишь ссылаются на них.

Полного PHB/Tasha/всех книг и русских переводов прозы не обещаем. Новых внешних источников нет: используется уже сохранённый SRD5.1 и существующий каталог метаданных. Названия RU — собственные проверенные переводы с EN для поиска, исходная проза SRD EN маркируется как EN. Не-SRD полнотекстовые записи создаются владельцем вручную в личной библиотеке. Импорт dnd.su/5e.tools, OCR, полная автоматизация эффектов, автоматическое развитие класса и расход ресурсов из текста не входят. Не вводится универсальный движок механик.

## Decisions

### 1. Данные и доказуемое покрытие
AbilityEntry: `{id,edition,kind,name{ru,en},text{en,ru?},scope{classId?,subclassId?,raceId?,parentId?},level?,prerequisiteText?,actionType?,source,review}`. kind = class_feature/subclass_feature/racial_trait/feat/option. Неизвестные level/actionType остаются null, требования текстовые. ID `srd51:feature:<scope>:<stable-key>` из явного manifest, не из локализованного имени/позиции в массиве. Одноимённые способности разных классов/редакций не склеиваются; варианты имеют parentId. Подтверждённые ссылки на заклинания используют прежние ID, не создают копий Spell.

Нормализация идёт офлайн из сохранённого корпуса. Manifest фиксирует source hash, страницы, границы каждого блока, таблицы/варианты, число принятых и требующих проверки записей по категориям. Колонки PDF проверяются вручную: regex-граница не доказывает полноты. Число способностей заранее не выдумывается; до merge данных публикуются точное число, manifest всех кандидатных блоков и список неопределённостей. Ни один блок не исчезает молча. Неуверенные поля помечаются review, не запускают правила. Публикация первого выпуска требует учёта всех целевых блоков SRD этих категорий; неоднозначные данные остаются текстом со ссылкой на страницу.

MagicItemEntry использует прежние934 ID и поля JSON. Генератор UI-проекции не переписывает исходные данные. Вариант выбирается явно по существующему srd_index; если его нет, не выдумывается новый статблок. Полный текст только в подтверждённых SRD-полях; metadata-only показывает имя/тип/редкость/настройку/книги/ссылку и «Описание не включено». Нулевые цена/вес/заряды вместо null запрещены. Инвентарь не получает придуманные бонусы.

### 2. Интерфейс и доступ
Главная: «Каталоги» → «Способности» / «Магические предметы», также открытие из соответствующей вкладки листа с явно выбранным получателем. Общий loader догружает небольшой сгенерированный JSON по выбранному каталогу, не весь PDF/SQLite и не при каждом входе. Ошибку/пустой результат/повторную загрузку показывать отдельно, лист остаётся доступным. Поиск по RU/EN, регистронезависимый, ё/е для поиска без изменения имён. Фильтры способностей: категория, класс/подкласс/раса, уровень если известен, источник; предметов: тип, редкость, настройка, наличие описания, источник. Фильтры комбинируются и сбрасываются. Карточка показывает происхождение, ограничения и неизвестные параметры. Доступность клавиатурой, фокус после закрытия, экран390px, состояния loading/error/empty обязательны.

### 3. Шаблон и экземпляр листа
Character.features[] и inventory[] TASK-004 остаются единственным хранилищем выбранных сущностей. Способность копируется как `{id,name,text,source,catalogueRef}`; предмет — `{id,ref,name,quantity,unitWeight,equipped,attuned,notes,catalogueRef,description}` с согласованными полями TASK-004. catalogueRef = `{kind,id,variantId?,revision}`. Точные дополнительные имена согласует исполнитель TASK-004; это предложение расширения его контракта, не обход его авторства. Публичный шаблон неизменяемый; каждый экземпляр получает новый instance ID. Два одинаковых предмета могут иметь независимые заряды/настройку/заметки. Правка или удаление шаблона не правит экземпляры; автосинхронизации нет.

«Добавить» показывает превью: герой-получатель, текст, вариант, количество, видимость, неизвестные поля. До подтверждения лист не меняется. По умолчанию предмет не экипирован и не настроен. Предупреждение о похожей уже выбранной способности не скрывает запись и не решает за пользователя допустимость повтора. Один operationId повторного запроса не добавляет второй экземпляр; намеренное второе добавление — новая операция. Сохраняем через серверный путь TASK-004 с ожидаемой версией/ACK, без собственной записи characters.data целиком. При конфликте — пересчитать превью с актуальным листом, не терять чужую правку.

Состав/сборку меняют владелец листа и мастер. Управляющий ресурсами и другой игрок могут просматривать каталог, но не добавлять умения/снаряжение в чужую сборку. Контроль токена/открытое перемещение не выдаёт это право. Отображение полного листа у участников — по решению TASK-004, не по приватности исходной библиотеки.

Старые features/inventory строки читаются без потерь через совместимый reader TASK-004. Каталог не парсит свободный текст в классы/предметы. Дополнение структурированного списка сохраняет исходную legacy-заметку; переход/поле записи согласуется с владельцем листа, старый текст не очищается.

### 4. Личные шаблоны
Отдельная `user_catalogue_entries`: id,owner_id,kind(feature|magic_item),data JSONB,revision,updated_at. Creature и таблица creatures не перегружаются чужими типами. Только собственник читает/меняет/удаляет; статус мастера не открывает чужую личную библиотеку. Лимиты:500 шаблонов суммарно этих двух типов на пользователя и64KiB UTF-8 на запись; квота creatures отдельная. Лимит и конкурентные вставки контролируются сервером; изменение требует ожидаемой revision и сообщает конфликт. Новая миграция, отдельные клиенты; никаких realtime-подписок кампании для личных записей.

Собственная ручная проза не попадает в публичный JSON, логи или общий поиск другого пользователя. В кампанию копируется только явно выбранный snapshot в лист; до сохранения пользователь видит, что его смогут читать участники, имеющие доступ к полному листу. Удаление личного шаблона не удаляет snapshot. Хранить личную библиотеку целиком в characters/campaign.data нельзя. Песочница — необязательный root catalogueEntries в прежнем rasputye-v2-db, версия и кампании сохранены; локальный режим не считается серверной защитой. Работа с изображениями книг не входит в первую версию этих двух каталогов, достаточно ручного текста.

### 5. Разделение исполнения и зависимости
| Порция | Результат | Предлагаемый исполнитель | Зависимость |
| --- | --- | --- | --- |
| A | SRD-manifest, нормализация способностей, read-only проекция предметов, валидатор/loader/tests | Эта сессия Codex | Подтверждение плана/границ |
| B | Личные шаблоны, RLS/квоты/CAS, sandbox/server API/tests | Эта сессия Codex после согласования SQL-границ | A; переиспользовать подходы #125 без изменения чужих таблиц |
| C | Главная/каталоги/карточки/поиск/выбор | Claude UI или назначенный им исполнитель | A, API B; согласовать точки входа #97 |
| D | Подключение к features/inventory и подтверждение экземпляров | Исполнитель TASK-004 или явно переданная им порция | Стабильный контракт #61, A/B/C |

До ACK C/D не назначены и не резервируются. Новые модули имеют независимые пути; sheet.js, screens.js, CSS и server model/sync изменяет только согласованный владелец. Issue/change учитывают порции, но новые task/plan/review-ветки не создаются. Будущий PR идёт непосредственно из постоянной codex/library в main с согласованным составом и полным SHA. Сейчас в истории codex/library есть модель #124, готовое хранение #125 и этот ещё не утверждённый план: порядок их интеграции согласуется с Claude, а не обходится новым снимком или переписыванием истории. Существующие PR/ветки автоматически не удаляются и не переносятся. Это применение прямого указания Яры от30.10, заменяющего прежний пункт AGENTS о снимках; канонический процесс обновляется отдельно его исполнителем. Родительские #61/#97 продолжаются независимо.

### 6. Совместимость и откат
Новые форматы описываются в docs/data.md и specs только при реализации/согласованной интеграции. Нынешние934 ID и таблицы исходного каталога неизменны. Новые SQL-миграции только добавляют личное хранение. Применение на проект после human review/merge; код откатывается revert merge. Сохранённые экземпляры содержат текст и не теряются при откате loader; удаление наполненных таблиц — отдельное решение. Удаление/сброс старых сохранений, перезапись всей кампании или смена ключей запрещены.

## Risks / Trade-offs
Главные риски: перепутанные границы PDF и одноимённые способности; утечка личных книг в общий каталог; расхождение с моделью листа TASK-004; потеря экземпляра/текста при конфликте; UI-конфликт с #97. Защита — manifest/hash/manual review, RLS, копии только по подтверждению, общий путь записи листа и назначенные владельцы файлов. Неполные SRD/metadata-карточки выглядят честно, а не как полный справочник всех книг. Полная автоматизация намеренно остаётся будущим объёмом, не непроверенным обещанием этого плана.
