# Design: мост голоса мастера «браузер → Discord-бот»

## Context

- Решение Яры 03.11: сайт управляет войсченджером, браузер обрабатывает голос, бот воспроизводит его в Discord. Без отдельного приложения и виртуального микрофона.
- Бот — `bots/discord` (#191): Node ≥ 22.12, `discord.js` 14, `@discordjs/voice` 0.19 (DAVE), ES-модули, один процесс. PoC подключается с `selfMute: true` и пишет входящий голос согласившихся по Discord ID. По design #191 бот работает на ПК разработчика, без облака.
- Сайт — buildless ES-модули на Vercel (HTTPS), вход через Supabase Auth/Discord (DEC-014). Своего сервера нет.
- Факты Discord, на которых держится дизайн:
  - серверный мьют (`voice_state.mute`) прекращает передачу голоса участника всем, включая ботов → во время NPC-режима запись #191 не получит исходную речь мастера;
  - voice state сообщает только флаг `mute`, без автора; автора видно в журнале аудита (`GUILD_AUDIT_LOG_ENTRY_CREATE`, `MEMBER_UPDATE`, ключ `mute`) при праве `VIEW_AUDIT_LOG`;
  - серверный мьют сохраняется на участнике гильдии и после выхода из голосового канала; изменить voice state участника вне голосового канала нельзя (ошибка API) — снятие приходится откладывать до его возвращения;
  - у одного голосового соединения бота одна исходящая дорожка → NPC-голос и будущая музыка DJ микшируются внутри бота (решение о едином потоке).

## Goals / Non-Goals

Цели: управляемый NPC-режим без двойного голоса, без обхода `self_mute` и чужих мьютов, с восстановлением после сбоев, измеряемой задержкой и сохранением исходной речи для транскрипции.

Не цели: STT и экспорт (следующий change), DJ, soundboard, клонирование голосов, отдельное приложение, изменение PoC записи сверх оговорённого.

## Архитектура

```
Браузер мастера (стол, серверный режим)                     Бот (bots/discord, модуль voice/)
getUserMedia ──► AudioWorklet DSP ──► WebCodecs Opus ─┐      ┌─► машина состояний NPC-режима
       │              (пресет)          (processed)   ├─WSS─►├─► jitter buffer ─► микшер ─► Discord
       └──────────────────────────────► Opus (raw) ───┘      ├─► модуль записи (#191): дорожка мастера + npc_on/off
                                                             └─► guild.members.edit(mute) + журнал аудита
```

Supabase Realtime как ретранслятор отклонён: ~50 сообщений/с на поток × 4 ч ≈ 720 тыс. сообщений за сессию при квоте Free 2 млн/месяц (DEC-014), плюс лишний сетевой участок и отсутствие бинарных кадров. WebRTC до бота избыточен для одного направления одного участника.

## Доступ браузера к боту — открытый вопрос (решают Яра и Dezmondy)

Страница `https://rasputye.vercel.app` может открыть только `wss://` с доверенным сертификатом; исключение — `ws://localhost`/`127.0.0.1`, но Chrome для запросов из публичной страницы в локальную сеть показывает запрос разрешения (Local Network Access).

| Вариант | Условие | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. Бот на ПК мастера, `ws://127.0.0.1:<port>` | мастер сам запускает бота | ноль инфраструктуры, минимальная задержка | бот привязан к ПК мастера; запрос доступа к локальной сети |
| B. Туннель (например, Cloudflare Tunnel) к ПК с ботом | домен или временный адрес туннеля | бот у Dezmondy, мастер где угодно | лишний сетевой участок, адрес/секрет туннеля в конфигурации |
| C. Бот на VPS с TLS | сервер и сертификат | стабильный адрес, 24/7 | расходы и администрирование — отдельное задание (AGENTS) |

Протокол от выбора не зависит; адрес бота задаёт мастер на сайте (хранится локально в браузере, не в БД). До решения реализация проверяется по варианту A.

## Привязка мастера

Без новых таблиц:
1. Мастер в Discord выполняет команду бота (например, `/voice pair`; имя — за Dezmondy). Бот отвечает эфемерно одноразовым кодом: 8 символов, TTL 5 мин, одно использование, только для мастера по правилам `permissions.js` #191.
2. Мастер вводит код на сайте; браузер отправляет его в `hello`. Бот связывает соединение с Discord ID мастера и гильдией.
3. В ответ `welcome` бот выдаёт `resumeToken` — секрет переподключения этой сессии моста (живёт до конца сессии или 12 ч). Браузер хранит его в `sessionStorage` и переподключается без нового кода.

Supabase JWT боту не передаётся: бот не получает ни ключей Supabase, ни доступа к БД. Имя NPC и id персонажа приходят от сайта как подписи для транскрипта, правами не являются. Проверка членства в кампании через JWT — возможное расширение, отдельным решением.

## Протокол (версия 1)

Одно WebSocket-соединение на мастера. Текстовые кадры — JSON управления, бинарные — аудио.

### Аудиокадр (бинарный, little-endian)

| Смещение | Поле | Тип | Смысл |
| --- | --- | --- | --- |
| 0 | `ver` | u8 | 1 |
| 1 | `stream` | u8 | 0 — processed (в Discord), 1 — raw (только запись) |
| 2 | `flags` | u16 | бит 0 — начало после разрыва, остальное 0 |
| 4 | `seq` | u32 | порядковый номер в потоке, с 0 на каждый `npc_on` |
| 8 | `captureUs` | u64 | время захвата первого сэмпла, мкс, часы браузера (`performance.timeOrigin + performance.now()`) |
| 16 | `opus` | … | один Opus-пакет: 48 кГц, 20 мс, 2 канала, VBR 64 кбит/с |

Два канала — по формату голоса Discord; mono-пакеты проверить отдельно, до этого не полагаться. Raw-поток — те же параметры, 32 кбит/с.

### Управление

Браузер → бот:
- `hello {proto:1, pairCode? | resumeToken?, client}`
- `npc_on {req, preset:{id,name}, npc:{name, characterId?}, raw:bool}` — запрос включения
- `npc_switch {preset, npc}` — смена пресета/NPC без изменения мьюта
- `npc_off {req, reason}` — выключение (`user`, `panic`, `device_lost`, `unload`)
- `hb {t}` — каждые 500 мс, пока соединение открыто
- `ping {t0}`

Бот → браузер:
- `welcome {session, resumeToken, discordUserId, guildId, channelId, caps:{maxLeaseMs, graceMs, raw}}`
- `voice_state {inChannel, selfMute, selfDeaf, serverMute, muteOwner:'bot'|'external'|null}` — при каждом изменении
- `state {state, reason?}` — переходы машины состояний
- `npc_ready {req}` — мьют подтверждён, можно слать processed
- `npc_stopped {req?, reason, unmuted:bool, pendingUnmute:bool}`
- `ack {stream, seq, recvUs}` — на каждый 10-й кадр
- `pong {t0, t1}` (`t1` — часы бота, мкс)
- `error {code, req?, detail?}`

Коды ошибок: `PROTO_MISMATCH`, `PAIR_INVALID`, `RESUME_INVALID`, `SUPERSEDED`, `BOT_NOT_IN_VOICE`, `MASTER_NOT_IN_CHANNEL`, `SELF_MUTED`, `SELF_DEAFENED`, `EXTERNALLY_MUTED`, `NO_PERMISSION` (`detail`: недостающее право), `MUTE_TIMEOUT`, `LEASE_EXPIRED`, `EXTERNAL_UNMUTE`, `MASTER_LEFT`, `BOT_VOICE_LOST`.

Второе соединение того же мастера получает сессию, первое — `error SUPERSEDED` и закрытие; воспроизведение от первого прекращается до приёма кадров второго.

## Машина состояний NPC-режима (бот)

```
IDLE ──npc_on──► ARMING ──проверки ок──► MUTING ──мьют подтверждён──► ACTIVE
  ▲                 │ отказ                  │ таймаут 3 с                 │ self_mute / self_deaf → PAUSED (кадры отбрасываются)
  │                 ▼                        ▼                             │ npc_off → DRAINING → UNMUTING → IDLE
  └──── error ◄─────┴────────────────────────┘                             │ lease 1,5 с → SUSPENDED
                                                                           │ внешний анмьют → STOPPED_EXTERNAL → IDLE
SUSPENDED ──resume за 15 с──► ACTIVE ;  ──grace истёк──► UNMUTING → IDLE
```

- **ARMING** — проверки по порядку, первая неудача → `error` и `IDLE`: бот в голосовом канале; мастер в том же канале; нет `self_mute`, `self_deaf`; нет серверного мьюта (`EXTERNALLY_MUTED` — бот не берёт мьют на себя и не говорит за мастера под ограничением модератора); у бота `MUTE_MEMBERS`, `SPEAK`, `VIEW_AUDIT_LOG`. Без `VIEW_AUDIT_LOG` режим не включается: иначе бот не отличит чужой мьют/анмьют.
- **MUTING** — сначала запись владения на диск бота (`{guildId, userId, session, mutedAt}`), затем `members.edit(userId, {mute:true}, reason:"rasputye:npc:<session>")`. Подтверждение — пришедший `voiceStateUpdate` с `mute:true`. Затем `npc_ready`. Таймаут 3 с → снять мьют, если он установлен ботом, удалить запись, `MUTE_TIMEOUT`.
- **ACTIVE** — кадры processed проходят jitter buffer (цель 60 мс, максимум 120 мс; опоздавшие отбрасываются) и воспроизводятся. Кадры, пришедшие вне ACTIVE, отбрасываются.
- **PAUSED** — `self_mute`/`self_deaf` мастера: воспроизведение и запись raw останавливаются, мьют держится. Снятие — возврат в ACTIVE. `npc_off` из PAUSED — обычное выключение.
- **DRAINING** — приём processed прекращён, буфер доигрывается (≤ 120 мс), затем UNMUTING.
- **UNMUTING** — снять мьют, только если владелец — бот. Если мастер не в голосовом канале — `pendingUnmute`, снятие при его следующем входе в голосовой канал гильдии. Запись владения удаляется после подтверждённого снятия.
- **Владение мьютом**: событие журнала аудита `MEMBER_UPDATE` с изменением `mute` мастера, исполнитель ≠ бот:
  - `mute → true` во время режима → `muteOwner = external`; воспроизведение останавливается (`EXTERNALLY_MUTED`), при выходе мьют не снимается;
  - `mute → false` во время режима → `EXTERNAL_UNMUTE`, воспроизведение останавливается немедленно (иначе два голоса), владение снимается, сам мьют бот больше не трогает.
  - Если журнал аудита недоступен или событие запоздало, при неоднозначности бот выбирает «не снимать мьют» и сообщает мастеру — лучше молчащий мастер, чем снятое чужое ограничение.
- **Перезапуск бота**: при старте для каждой записи владения — если мастер всё ещё под мьютом и в журнале аудита после `mutedAt` нет чужих изменений мьюта, снять (или отложить до входа в канал); иначе удалить запись без снятия.
- **Потеря голосового соединения бота** (`BOT_VOICE_LOST`): воспроизведение невозможно → сразу UNMUTING своего мьюта, мастер говорит обычным голосом; восстановление соединения не включает режим само.
- **Мастер вышел из канала**: `MASTER_LEFT`, DRAINING → UNMUTING с `pendingUnmute`.

Порядок, исключающий двойной голос: включение — мьют подтверждён → `npc_ready` → браузер начинает слать processed; выключение — браузер прекращает слать → бот доигрывает буфер → снимает мьют. Возможная цена — пауза 100–300 мс тишины мастера на переходах, это приемлемо; перекрытие голосов — нет.

## Сбои и закрытие вкладки

- **Lease**: бот считает соединение живым, пока приходят кадры или `hb`. 1,5 с тишины → SUSPENDED: воспроизведение прекращается сразу, мьют держится grace 15 с. Переподключение с `resumeToken` и новым `npc_on` за grace → ACTIVE без снятия и повторной постановки мьюта. Grace истёк → UNMUTING.
- **Закрытие вкладки**: браузер пытается отправить `npc_off {reason:'unload'}` в `pagehide`, но корректность обеспечивает lease, а не это событие.
- **Фоновая вкладка**: AudioWorklet и WebSocket продолжают работать; таймеры `hb` могут замедляться, поэтому lease считает и аудиокадры, а не только `hb`.
- **Потеря микрофона** (`track.onended`, смена устройства): браузер отправляет `npc_off {reason:'device_lost'}` и показывает мастеру причину.
- **Ошибка DSP/кодера**: браузер прекращает отправку и выключает режим; повреждённый звук не уходит молча.
- **Кнопка «Обычный голос»** (panic): `npc_off {reason:'panic'}` и мгновенная остановка отправки, без подтверждений.

## Браузер

- Захват: `getUserMedia({audio:{echoCancellation:false, noiseSuppression:true, autoGainControl:false, channelCount:1, sampleRate:48000}})`; AEC выключен, потому что голос в Discord воспроизводит бот, а не страница.
- `AudioWorklet` DSP. Пресеты — набор параметров одной цепочки: pitch shift (granular/PSOLA, ±12 полутонов), формантный сдвиг, EQ, сатурация, кольцевая модуляция, реверберация, гейт. Пресет — данные; хранение пресетов — следующим решением (сначала локально, без схемы БД).
- Кодирование: `AudioEncoder` (WebCodecs, `opus`, 48 кГц, 2 канала, `frameDuration 20000`); без WebCodecs режим недоступен с понятным сообщением.
- Предпрослушивание: локальный вывод обработанного сигнала в наушники, независимо от моста.
- Интерфейс: панель NPC мастера на столе (серверный режим), состояние моста и голосового состояния, причина отказа, задержка, кнопка «Обычный голос». Подключение — `views/table/index.js` (mount/unmount), кнопка — `chrome.js`; новые файлы `dist/js/audio/**`, `dist/css/audio.css`. Точные места — по согласованию с sol0139.

## Задержка

Измеряется, а не предполагается. Участки:
1. захват → начало обработки: `AudioContext.baseLatency` + размер блока worklet;
2. DSP: время обработки блока (`performance.now()` в worklet), окно алгоритма pitch shift;
3. кодирование: `captureUs` → выход `AudioEncoder`;
4. сеть: `recvUs` из `ack` минус `captureUs` с поправкой на смещение часов по `ping/pong` (минимальный RTT из скользящего окна);
5. буфер бота: фактическая глубина jitter buffer;
6. Discord → слушатели: напрямую не измерить; оценивается loopback-тестом (второй аккаунт записывает канал вместе с эталонным щелчком).

Мастеру показываются p50/p95 участков 1–5 за последние 30 с. Ориентир для приёмки предлагается утвердить по итогам измерений прототипа: добавленная задержка до отправки ботом p95 ≤ 150 мс в проводной сети. Это цель для проверки, не обещание.

## Транскрипция: что готовит этот change

- Raw-поток шлётся только при `npc_on {raw:true}`, который сайт выставляет, если у бота идёт запись #191 и мастер дал в ней согласие (бот сообщает это в `welcome.caps.raw` и `voice_state`). Raw не воспроизводится в Discord.
- Модуль записи пишет raw как дорожку мастера (его Discord ID) теми же фрагментами Ogg/Opus, что и входящий голос, и добавляет в `manifest.jsonl` события `npc_on {preset, npcName, characterId?}`, `npc_switch`, `npc_off` с таймкодами сессии. Как именно модуль записи принимает второй источник — решает Dezmondy.
- Следующий change (транскрипция) подписывает сегменты, попавшие в интервал NPC, как «Мастер (как <NPC>)», а вне интервала — «Мастер» или его персонаж; хранение 72 ч и удаление — там же, по плану #191.

## Риски

- Отправка и приём голоса ботами Discord плохо документированы; DAVE-переходы при входе участников могут давать короткие сбои — проверить вживую.
- Журнал аудита приходит с задержкой; окно неоднозначности закрывается правилом «при сомнении мьют не снимать».
- Мьют, установленный ботом, видят все участники; отображение «изменённый голос мастера» в Discord — у бота, а не у мастера (ожидаемо, объясняется в UI).
- Микширование с DJ требует декодирования и повторного кодирования в боте — нагрузка и задержка растут; решение Dezmondy.
- Pitch shift с высоким качеством добавляет 20–40 мс алгоритмического окна; качество и задержку выбирать по измерениям.

## Migration / откат

Сайт: новые файлы, хуки за флагом; без хуков и бота сайт работает как раньше. Бот: модуль `voice/` и команда привязки, выключаемые настройкой; PoC записи не меняется, кроме согласованного второго источника. Откат — revert. Записи владения мьютом снимаются ботом при старте по правилам выше.

## Проверки

- Юнит-тесты без сети: машина состояний (все переходы, гонки `npc_off` ↔ `npc_ready`, lease, grace, внешний мьют/анмьют, перезапуск с записью владения, отложенное снятие); разбор кадров; jitter buffer; смещение часов.
- Браузер: DSP-пресеты на эталонном сигнале, отсутствие кадров вне `npc_ready`, panic, потеря устройства.
- Живая приёмка на тестовом сервере: включение/выключение 50 раз без двойного голоса; закрытие вкладки, обрыв сети, перезапуск бота; `self_mute` во время режима; мьют и анмьют модератором во время режима; мастер выходит из канала; измерение задержки участков 1–5 и loopback.
- Репозиторий: `npm ci`, `spec:validate`, `spec:validate:archive`, `npm test`.
