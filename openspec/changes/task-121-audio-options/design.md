# Design: три плана голоса и транскрибации

## Context

TASK-121 / [#121](https://github.com/YGXVI/tavern/issues/121). Ревизия 1, 2026-10-30 (+05:00), Яра / Codex. Основание и участники — [proposal.md](proposal.md). База `bf3b426b8a05bab35bac655488fb6439c70fa419`. Все описанные ниже API и таблицы — предложения, не существующие функции.

Наблюдения по коду: `SERVER_ENABLED=false`, есть preview `?server=1`, Supabase Auth PKCE и серверный адаптер. В SQL `public.is_member(c text)` проверяет `auth.uid()` и `campaign_members.status='active'`; `is_master` добавляет `role='master'`. Идентификатор кампании — text, пользователя — UUID. Голосовых браузерных API в `dist/js` на этой базе нет.

Стол монтируется через `mountTable` в `views/table/index.js`, интерфейс перестраивается через `renderChrome` в `chrome.js`. Аудиодвижок нельзя пересоздавать при каждом рендере. Выход из кампании должен освобождать микрофон и соединение. Точный hook teardown и mount panel — один из вопросов Claude.

## Goals / Non-Goals

Пилот: одна кампания, 4–6 участников, настольные Chrome/Edge и реальные устройства группы, русская речь, 60 минут непрерывной проверки и затем одна игровая сессия. Сроки ниже — трудозатраты одного разработчика после выбора подхода и доступности инфраструктуры, не обещание даты релиза.

Не включать в первый пилот: нейросетевое клонирование голоса, драйвер виртуального микрофона собственной разработки, захват всего системного звука, видео, позиционный звук, автоматическое опубликование хроники. Safari/Firefox/мобильные устройства расширяют матрицу после измерений, их поддержка не заявляется заранее.

## Decisions

### Матрица выбора

| Критерий | A — собственный чат | B — Discord-бот | C — Discord + запись в сайте |
| --- | --- | --- | --- |
| Разговор | В сайте через WebRTC/SFU | В обычном канале Discord | В обычном канале Discord |
| Источник записи | Отдельные дорожки участников | Приём потоков ботом | Свой микрофон каждого участника |
| Голоса NPC | DSP браузера до отправки | Готовый внешний войсченджер | Готовый внешний войсченджер |
| Установка игрокам | Не требуется | Не требуется | Не требуется, сайт должен оставаться открытым |
| Установка мастеру | Не требуется | Для внешнего войсченджера | Для внешнего войсченджера |
| Основной риск | Сеть, TURN, эксплуатация SFU | Недокументированный receive, DAVE | Два приложения используют микрофон, разные часы, фоновые вкладки |
| Пилот, предварительно | 20–35 рабочих дней | 10–20 рабочих дней | 10–15 рабочих дней |
| Полнота трёх функций | Все внутри проекта | Чат и DSP внешние | Чат и DSP внешние; промежуточный этап |

Рекомендация автора: сначала короткая проверка C, затем общий транскрипт и при успешном пилоте переход к A. Если нужна единая кнопка разговора и голосов NPC сразу — выбрать A. Если участники не хотят включать запись на сайте — проверить B. Не строить три транспорта одновременно.

### План A: голосовой чат внутри «Распутья»

Архитектура: сайт → Web Audio/DSP → WebRTC → LiveKit SFU → игроки. Отдельный доверенный recorder подключается при согласованной записи → приватное хранилище → очередь STT → редактор. Supabase обслуживает идентичность, метаданные и доступ; звуковые пакеты не идут через Realtime.

1. **Технический срез, 2–3 дня.** Изолированная страница с двумя, затем шестью подключениями. Проверить TURN с ограниченной сетью, смену микрофона, переподключение. Выход: измеренный сценарий на двух физических устройствах, сравнение self-hosted и managed размещения по эксплуатации и бюджету. Новая платная подписка не создаётся автоматически.
2. **Комната кампании, 4–7 дней.** Серверный token endpoint валидирует Supabase JWT и актуальное активное членство; токен ограничен комнатой кампании и коротким сроком. UI: join/leave, mute/deafen, выбор устройства, активный говорящий, громкость. Исключение из кампании отключает участника на медиасервере, а не только скрывает UI.
3. **Запись и STT, 6–10 дней.** Отдельные дорожки, наблюдаемое состояние записи, остановка при отзыве согласия, повтор обработки, редактор с временными метками. Ошибка записи не роняет разговор. При E2EE доверенный recorder получает ключи как явный участник; не обещать сквозную секретность от сервиса, который должен распознавать звук.
4. **DSP, 4–7 дней.** AudioWorklet/WASM для pitch/formant при необходимости, EQ и умеренные эффекты; исходный голос, 3 различимых пресета, плавное переключение без щелчков, мониторинг только по явному включению в наушниках. Поток для STT по возможности брать до художественных эффектов, с отдельным явным согласием.
5. **Пилот и исправления, 4–8 дней.** Проверка длинной сессии, выхода, отказа устройств, доступа и восстановления; решение о дальнейшем расширении.

Критерии пилота A: шесть участников разговаривают 60 минут; p95 mouth-to-ear ≤250 мс в проверенной географии, добавка DSP p95 ≤50 мс (целевые показатели, измерить); разрыв и восстановление отмечены; посторонний и pending участник не входят; исключённый отключается; стоп выключает capture, выход закрывает аудиоресурсы. При невыполнении задержки упрощаем DSP или отключаем эффекты, разговор сохраняется.

### План B: Discord-бот и внешний войсченджер

Архитектура: микрофон мастера → локальный войсченджер → виртуальное устройство → Discord. Отдельный bot worker в канале получает дорожки → тот же ingest/STT → сайт. Бот не подменяет микрофон пользователя; его ретрансляция не должна добавлять вторую копию голоса.

1. **Проверка receive/DAVE, максимум 2–3 дня.** Закрепить библиотеку и runtime в отдельном сервисе; проверить доступ к отдельным потокам двух участников, одновременную речь, тишину, rejoin, 60 минут работы. Только тестовые/явно согласованные записи, без отправки третьим сторонам по умолчанию. Отдельно проверить актуальные условия Discord для выбранной обработки и хранения.
2. **Связь канала с кампанией, 2–3 дня.** Мастер связывает доступный серверный канал, бот работает только там. Discord ID связывается с подтверждённым профилем, не с nickname. Неизвестный участник и поздний вход блокируют/приостанавливают запись до согласия; права на канал и права кампании проверяются раздельно. Первый пилот только для серверного voice channel, без обещания записи личных звонков.
3. **Ingest, STT, редактор, 4–8 дней.** Использовать общий контракт ниже. При потере потока ставить gap и не генерировать текст тишины. Вход/выход бота и состояние записи видны группе.
4. **Пресеты мастера и пилот, 2–6 дней.** Выбрать существующий войсченджер по ОС мастера, провести настройку и тест совместимости с шумоподавлением Discord. Записать инструкцию, ограничение: в транскрипт обычно приходит уже обработанный голос.

Условие отказа B: за 2–3 дня нет воспроизводимого раздельного приёма с DAVE и rejoin → B не расширять, перейти на C или A. Не чинить клиент Discord модификациями и не превращать исследование в разработку собственного голосового протокола.

### План C: запись микрофонов на сайте, разговор в Discord

Архитектура: каждый участник говорит в Discord и отдельно разрешает сайту записывать свой микрофон. Сайт собирает только этот микрофон; голоса других берутся из их собственных записей, не из системного микса. Войсченджер мастера остаётся внешним. Общие ingest/STT/editor впоследствии используются в A.

1. **Проверка устройств, 1–2 дня.** Два приложения одновременно получают микрофон; проверить ОС группы, headset, настройки echo cancellation и вкладку в фоне. Участник видит уровень именно выбранного входа. Если исходный микрофон недоступен вместе с виртуальным, явно выбрать обработанный поток и отметить это в Track.
2. **Локальный capture/upload, 3–4 дня.** MediaRecorder с MIME feature detection, последовательные чанки, bounded retry и явный статус незагруженного хвоста. Куски одной записи могут не декодироваться по отдельности: сервер собирает контейнер по seq, проверяет целостность и только затем делает STT. Не вычислять время как seq × timeslice: dataavailable не является точным таймером.
3. **Общий STT и редактор, 4–6 дней.** Раздельное распознавание дорожек, совмещение по временной шкале, ручная коррекция смещения и говорящего, экспорт. Сначала после stop/finalize, живые субтитры не входят.
4. **Пилот, 2–3 дня.** 4–6 участников, повторная отправка после обрыва, 60 минут записи, reload с предупреждением о потере несохранённого хвоста. Если потребуется восстановление после reload — отдельный лимитированный IndexedDB spool с явной политикой удаления; не обещать его без реализации.

Синхронизация: сервер возвращает epoch сессии; клиент измеряет offset и RTT несколькими запросами, затем хранит монотонное время capture. При rejoin создаётся новая Track и новая калибровка. Оценить дрейф в длинной записи; целевой разброс совмещения ≤250 мс после коррекции. Это не точная синхронизация ОС; UI разрешает сдвинуть дорожку вручную.

Критерий отказа C: один из основных компьютеров группы не может стабильно писать микрофон одновременно с Discord либо вкладки регулярно теряют существенные фрагменты → не расширять матрицу, выбрать B или A. Без участника на сайте его речь отсутствует; «полная запись канала» не заявляется.

### Общая модель и API (эскиз для выбранного плана)

Аудио живёт отдельно от JSON кампании, боевого лога и листов. Сервер выставляет доверенные поля; клиент не назначает себе owner/user/campaign через payload.

| Объект | Предлагаемые поля |
| --- | --- |
| AudioSession | id UUID, campaign_id text, created_by UUID, source web/discord/local, status, epoch, retention_until, deletion_state |
| Consent | session_id, user_id, scope raw/processed/transcript, version, granted_at, revoked_at; явно охватывает выбранный способ записи |
| Track | id, session_id, participant_user_id, source_track_id, input_kind raw/processed, codec, sample_rate, clock_offset_ms, discontinuities |
| Chunk | track_id, seq, object_key, checksum, byte_size, capture_start/end, receipt; unique(track_id, seq) |
| Job | session_id/track_id, engine_version, status queued/running/failed/complete, attempts, input_checksum; идемпотентный ключ |
| Segment | id, track_id, start_ms/end_ms, text, speaker_user_id, performed_character_id nullable, revision, edited_by; provenance original/edited |

Эскиз endpoints: POST session, POST consent/revoke, POST track, POST chunk-upload-url, POST chunk-commit, POST finalize, GET session/transcript, PATCH segment с expected_revision, DELETE session. Только A: POST room-token. Только B: link Discord channel и bot ingest с отдельным сервисным доступом. Для ingest проверять согласие/членство и квоту при выдаче URL и commit; короткий URL ограничивать одним объектом, файл до commit не доступен чтению. Удалённые сессии нельзя воскресить поздним commit/webhook.

Доступ пилота: мастер создаёт сессию; каждый участник сам подтверждает запись; запись всей группы начинается после согласия присутствующих. При позднем входе/отзыве — пауза общего recorder до нового состояния согласия. В C локальный capture участника прекращается немедленно при отзыве. Просмотр сырых дорожек и исходного транскрипта по умолчанию только мастеру; игрок получает отдельно опубликованный материал. Мастер не получает право записывать отказавшего участника. При потере активного членства сервер прекращает доступ к приватным данным и новым загрузкам; поведение текущей комнаты принудительно синхронизируется отдельно от срока токена.

Рекомендованная политика для пилота: сырое аудио до 7 дней, транскрипт до удаления сессии, публикация хроники отдельно. Это предложение для выбора, не действующая политика. Удаление session ставит tombstone, останавливает jobs и ingest, удаляет blobs/сырой текст/черновики, сохраняет минимальное техническое подтверждение без содержания. Уже опубликованную/скачанную хронику нельзя обещать отозвать из внешних копий; в продукте явно показать отдельную публикацию и её жизненный цикл.

STT: интерфейс backend engine заменяемый. Сравнить self-hosted faster-whisper и один облачный сервис после разрешения передачи/затрат. Одинаковый RU набор с ручной эталонной разметкой: 10 минут, 2+ говорящих, имена D&D, тишина, перебивания. Записать WER, ошибки имён, пропуски, скорость, стоимость на час. Цель пилота WER ≤20% на согласованном наборе; числовой результат измеряется, не предполагается. Для раздельных дорожек говорящий — подтверждённый аккаунт; персонаж/NPC — явная пометка или ручное исправление, не голосовая биометрия. Для единственного смешанного импорта diarization — отдельная операция с ручной привязкой. Повтор STT не стирает ручную редакцию.

### Граница файлов и подключения

В выбранной реализации Codex предлагает новые `dist/js/audio/{capture,session,clock,dsp,transcript}.js`, `dist/js/audio/worklets/**`, изолированный `dist/js/views/table/audio-panel.js` и `dist/css/audio.css`; service API/worker — отдельный пакет вне dist, точное размещение после выбора. Новые SQL-миграции и отдельные audio tables/bucket; не менять уже применённые миграции.

Claude предлагается указать hook создания/teardown в index.js и слот кнопки в chrome.js. Нужен один контроллер на mount, состояние живёт вне перерисовываемого DOM. При удалении панели из DOM запись не должна скрытно продолжаться без индикатора. Точка выхода останавливает tracks, recorder, worklets, peer connection и listeners. Не менять общий campaign JSON, sheet.js, token RPC, sync.js/model.js. Указанные файлы не считаются переданными до конкретного ответа.

Уточнение после повторной сверки той же базы: `mountTable` уже возвращает объект с `unmount()`; предлагаемый controller создаётся рядом с `ctx.panels`, его dispose вызывается в этом unmount. В chrome.js события `data-act` делегируются `ctx.panels.action`, поэтому только кнопки недостаточно: либо минимальный отдельный audio-action handler перед существующим делегированием, либо один routing case в panels.js. Точное решение остаётся предметом ответа Claude; не объявлять panels.js переданным. Проверку SQL helpers выполнять в контексте проверенного пользовательского JWT: service-role соединение само по себе не задаёт `auth.uid()` этого пользователя. Привилегированному worker нужен отдельный ограниченный контракт; не пересылать ему произвольный user_id как доказательство прав.

### Стоимость и критерий выбора

Сначала считать нагрузку: 5 участников × 4 ч × 4 встречи = 80 участнико-часов/месяц; STT — до 80 дорожко-часов до удаления тишины, не 16 часов встречи. При mono Opus 32 кбит/с четыре часа одной дорожки ≈57,6 МБ; вся группа ≈288 МБ без накладных расходов. Реальный кодек/битрейт измерить, временный PCM может быть существенно больше.

A добавляет SFU/TURN, трафик и recorder. B добавляет постоянно работающий bot worker, C — upload API; всем нужны STT/storage и эксплуатация. Для self-hosted считать сервер и обслуживание, для managed — participant minutes, egress и storage отдельно. Цены и бюджет не фиксировать по памяти: после выбора сервиса получить актуальный расчёт и лимит расходов. Не создавать подписки или GPU-инстансы в рамках исследования.

### Другие варианты Discord

Activity полезна для показа стола в Discord, но сама по себе не даёт готовую замену исходящего микрофона и запись всего звонка. Модификацию клиента/расширение браузера не выбирать базой: придётся поддерживать внутренности чужого клиента и отдельные ограничения платформы.

Официальный Social SDK имеет аудиоколбэки и поддерживает эффекты. Это четвёртый возможный будущий путь для нативного клиента; документированные C++/Unity/Unreal интеграции не вставляются напрямую в наш JS-сайт. Проверка такого пути включает отдельный desktop прототип и условия production доступа SDK; не подменять им простое расширение Discord.

## Risks / Trade-offs

- Receive Discord нестабилен → ограниченный по времени прототип B; не зависеть от него до проверки.
- Фоновая вкладка/устройство дают gaps → фиксировать разрывы и фактическую длительность; не выдавать неполный транскрипт за полный.
- Эффекты ухудшают STT → отдельная исходная дорожка только при согласии, иначе оценивать распознавание обработанного голоса.
- Идемпотентность upload не означает идемпотентность обработки → checksum/job key + сохранение пользовательской ревизии текста.
- Связь с кампанией устаревает → проверки на сервере при операциях и принудительное отключение текущего медиаклиента.
- Пересечения с #61/#97 → изолированные audio modules; общие hooks только после конкретного ответа Claude.

## Migration Plan

В этой документационной ревизии миграций и deploy нет. Для реализации: сначала контракт и новые таблицы с RLS; затем API/worker; затем audio feature flag, выключенный для всех; пилот кампании; расширение после измерений. Текущую песочницу не отправлять на сервер автоматически.

Откат: отключить аудиофункцию, запретить новые capture/upload/token, остановить jobs и завершить соединения; игровой стол продолжает работу. Метаданные/приватные записи не удалять откатом кода, их удаляет отдельная операция по принятой политике. Выполненные SQL не переписывать задним числом.
