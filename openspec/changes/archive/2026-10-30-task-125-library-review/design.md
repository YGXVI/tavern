# Design

## Идентичность
creatures имеет PK (owner_id,id). Каждый server upsert указывает эту пару, list/delete фильтруют owner_id. source_id кампании — только происхождение, не глобальный ключ личной записи. В песочнице ключ JSON.stringify([ownerId,id]); старый [id] читается и мигрируется только своим владельцем, составная копия приоритетна. Квота считает уникальные ID владельца.

## Файлы
Внутренний library_storage_usage(owner_id,files,bytes) с CHECK 200 / 104857600, без прямого доступа API. BEFORE Storage guard проверяет путь, блокирует строку владельца и защищает ссылки; AFTER INSERT/UPDATE/DELETE атомарно меняет количество/разницу байтов. AFTER не считает upsert-update второй вставкой. metadata.size — фактический размер; предварительная откатываемая проверка Storage может не иметь размера и учитывается как 0 байт до rollback. contentLength не используется: в multipart запросе он включает границы/служебные поля и может превышать 5 МиБ у допустимого файла. Квота относится к сохранённым объектам; транзитный сетевой поток ей не ограничивается.

Сохранение/удаление Creature получает ту же блокировку. Личные img/statblockImage должны ссылаться на существующий файл своего владельца. Удаление файла проверяет обе ссылки во всех личных creatures этого владельца; после последней ссылки файл можно удалить. BEFORE guards отвергают чужого authenticated/anon до проверки существования, не создавая новый oracle. Parent cascade не воссоздаёт счётчик удалённого профиля.

Снимок кампании не может хранить library: в img/statblockImage: place_creature Claude сначала копирует изображение в кампанию. Управление campaign copies и UI не реализуются этой порцией.

## Очистка и клиент
library_image_usage() и library_unused_images() возвращают только свои итоговые числа/сирот. cleanupUnusedLibraryImages() вызывается явно, удаляет через Storage remove и проверяет ACK каждой операции; возвращает removed/failed. До UI-подтверждения Claude фоновой очистки нет. Ошибка гонки или Storage не выдаётся за успешное удаление. Core проверяет смену пользователя/режима, серверные сведения не записывает в sandbox. В песочнице эти серверные методы недоступны, общий IndexedDB не удаляется.

## Совместимость и проверка
Supabase рекомендует не менять storage schema ([документация](https://supabase.com/docs/guides/storage/schema/design)); добавлены только наши triggers, пишущие собственный счётчик, без изменения metadata из app SQL. Удаление — [Storage API](https://supabase.com/docs/guides/storage/management/delete-objects). По исходникам [uploader](https://github.com/supabase/storage/blob/master/src/storage/uploader.ts) предварительная проверка разрешений откатывается, окончательная запись содержит metadata фактического файла. Это исследование текущих исходников, не доказательство версии в живом проекте. При обновлениях Storage и до включения uploads нужен HTTP smoke test размера/квоты/upsert/delete; локальные schema stubs это не проверяют.

Изолированный PostgreSQL проверяет реальные роли, ограничения, каскады, несколько ссылок и гонки строк/числа файлов/байтов/сохранения против удаления. При отказе квоты Storage API отвечает за очистку временных backend bytes; app SQL не удаляет storage.objects. Рабочая БД не затрагивается, применённые миграции не переименовываются. В Git только ещё не применённый creature_library получает 130000; порядок #126 → #150 → TASK-004 согласован координатором. Откат — revert кода; удаление данных и counters отдельно согласуется.
