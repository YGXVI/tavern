# Локальный демонстрационный вход

## Purpose

Базовое поведение GitHub main после TASK-007 / DEC-011 (2026-10-29). Ниже нормативные требования текущей версии. Дополнительный контекст сохраняет прежние планы и ограничения; его целевые разделы не означают готовность.

## Requirements

### Requirement: Локальный демонстрационный вход

Приложение SHALL позволять выбрать демо-аккаунт или ник без настоящего Discord OAuth; выбранный пользователь хранится отдельно для каждой вкладки.

#### Scenario: Базовый сценарий

- **WHEN** пользователь выбирает демо-аккаунт
- **THEN** вкладка использует его userId, а роль определяется членством в кампании; личность сервером не проверяется

## Контекст, ограничения и будущие этапы

Материал прежнего `docs/features/auth.md` перенесён без потери целей. Описания старого прототипа относятся к `/legacy/`. При устаревшем описании текущего состояния ориентироваться на Requirements выше и код; изменение требований оформлять delta spec.

# Вход и выбор роли

## Статус и зависимости

Новый интерфейс (TASK-007, DEC-011) показывает **имитацию** входа через Discord. Настоящих аккаунтов, проверки личности и сервера нет; провайдер входа не выбран (DEC-008 открыт, TASK-002/003 не назначены — резервировать в [../status.md](../../../docs/status.md)). Прежний экран выбора роли сохранён в `dist/legacy/`.

## Цель

Пользователь выбирает, кем участвует в конкретной кампании. Мастер администрирует её, игрок управляет своим героем. В другой кампании тот же аккаунт может иметь другую роль.

## Сейчас

Файлы: `dist/js/core/auth.js`, `dist/js/views/screens.js` (`mountLogin`, `openOAuth`), маршруты в `dist/js/main.js`.

- `#/login` — экран входа по макету; кнопка «Войти через Discord» открывает окно, похожее на экран разрешений Discord: выбор одного из демо-аккаунтов (sol0139, Ася, Яра, Тимур, Ника, Рома) или свой ник. Никаких запросов в сеть, паролей и токенов.
- «Вход» — запись `{userId}` в `sessionStorage` (`rasputye-v2-session`): у каждой вкладки свой человек, поэтому в одной вкладке можно быть мастером, в другой — игроком. Новая вкладка подставляет последнего (`rasputye-v2-last-user`), кроме ссылки-приглашения.
- Роль не выбирается на входе: она берётся из членства в конкретной кампании (DEC-005). Меню пользователя: сменить аккаунт, сбросить демо-данные, выйти.

Это демонстрация, а не авторизация: любой может выбрать любой аккаунт, данные лежат в браузере. Старый ключ `rasputye-session-v1` и `dist/access.js` используются только прототипом в `dist/legacy/`.

## Целевая версия

Создание кампаний и приглашения описаны отдельно в [campaigns.md](../campaigns/spec.md).

Аккаунт → список доступных кампаний → создание кампании мастером или принятие приглашения игроком → назначенный/созданный герой → общий стол. Нельзя стать мастером чужой кампании, просто выбрав карточку. Роль назначает сервер по членству, а не `localStorage`.

## Критерии приёмки сервера

- Создание кампании выдаёт создателю членство мастера только в этой кампании.
- Приглашение ограничено кампанией, имеет понятные состояния недействительно/истекло/отозвано; детали механизма согласовать в TASK-002.
- Игрок не получает закрытые заметки, скрытые сцены и чужие изменяемые данные ни через UI, ни через API.
- Подмена роли/ID и доступ к другой кампании отклоняются сервером; тестировать отрицательные сценарии.
- Выход, восстановление входа, отсутствие кампаний, удалённый герой и потеря доступа обработаны явно.
- Миграция локальной демонстрации описана до замены ключей.

## Границы работы

Не внедрять второго поставщика входа, новую БД, социальные профили и глобальную роль «мастер» без решения. Не заменять существующий экран новой несогласованной реализацией: замена в TASK-007 согласована владельцем (DEC-011). Настоящий Discord OAuth подключать только после DEC-008 — сюда придёт ответ провайдера вместо `signIn()` в `dist/js/core/auth.js`. `dist/js/main.js`, `dist/index.html` — общие файлы, их резервировать одному исполнителю.
