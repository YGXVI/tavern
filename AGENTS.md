# Распутье: общие правила для Codex и Claude

Эти правила действуют для всего репозитория. CLAUDE.md только подключает этот файл; отдельные правила для двух агентов не создаём. Прямое задание пользователя имеет приоритет. При противоречии не затирайте решения коллеги молча.

## Сначала прочитать

1. `docs/vision.md` — продукт и границы.
2. `docs/status.md` — текущая работа, владельцы и передача.
3. `docs/decisions.md` — принятые решения.
4. `docs/data.md`, `docs/glossary.md` и спецификацию затронутой функции из `docs/features/`.
5. Актуальные изменения `main` и открытые PR. Локальная копия может отставать от GitHub.

## Как не мешать друг другу

- Одна задача — один ответственный исполнитель: человек + агент + идентификатор задачи. Не назначайте коллегу или другого агента без его согласия. Свободная функция не считается вашей автоматически.
- До изменения кода опубликуйте заявку в таблице `docs/status.md`: ID, исполнитель, статус, ветка, базовый commit, затрагиваемые файлы, зависимости и время обновления с часовым поясом. Только локальная запись не резервирует задачу.
- Заявку публикуют отдельным небольшим commit в `main`, меняющим только таблицу задач/передачу в `docs/status.md`. Перед отправкой перечитайте актуальный файл. Используйте обычный fast-forward или проверку ожидаемого SHA; при конфликте перечитайте обе заявки и сохраните их обе. Не заменяйте весь файл старой копией.
- Код и остальные документы — через отдельную ветку `codex/<task-id>-<slug>` или `claude/<task-id>-<slug>` от свежего `main` и PR. Каждому агенту — собственный checkout/worktree; не работайте одновременно в одной папке. Не переключайте ветку в рабочей копии коллеги.
- Перед началом убедитесь, что опубликована именно ваша заявка и нет пересечения с активной задачей. Пересечение файлов, DOM-контракта, схемы или API означает зависимость: согласуйте владельца общего изменения, дождитесь его PR либо разделите работу. Не правьте один общий файл параллельно даже «в разных местах» без согласованного плана.
- Заявка — соглашение команды, не техническая блокировка. При невозможности опубликовать её подготовьте спецификацию/дифф в своей ветке и сообщите о блокере. Не объявляйте резервирование состоявшимся.
- Не снимайте чужую заявку по давности. Пауза, передача и смена ответственного требуют явной передачи или решения владельца проекта. Обновляйте статус при начале, смене объёма, передаче и завершении; не ставьте `done` по факту написания кода без проверки и интеграции.
- Не запускайте другого агента для той же задачи без согласованного деления файлов. Для задачи не требуется переписываться с коллегами от имени пользователя.

## Общие участки и интеграция

| Участок | Правило |
| --- | --- |
| `dist/app.js`, `dist/index.html` | Сейчас здесь много функций; один активный исполнитель на файл. Извлечение модулей — отдельная согласованная задача. |
| `dist/style.css`, `dist/themes.css`, `dist/entry.css` | Общие селекторы и токены согласовать до изменения. Проверять светлую и тёмную темы. |
| `dist/access.js`, ключи localStorage, будущие API/миграции | Менять вместе с контрактом в `docs/data.md` и записью решения. |
| `package.json`, `.openai/hosting.json`, CI и конфигурация хостинга | Один ответственный на задачу; не менять платформу и зависимости попутно. |
| `docs/status.md`, `docs/decisions.md` | Сохранять чужие записи; записи решений добавлять с новым ID. |

- Не делайте `reset --hard`, `clean`, force-push, переписывание общей истории или массовую замену файлов, чтобы убрать чужие изменения. При конфликте сначала понять обе версии.
- Не мержите свой PR автоматически. Владелец проекта или явно назначенный им интегратор проверяет и объединяет PR по одному, начиная с зависимостей. Новые изменения `main` сначала учесть в ветке и повторить затронутые проверки.
- В PR укажите результат, затронутые файлы/контракты, задачу, зависимости, проверки, ограничения и миграцию при необходимости. Не смешивайте переработку архитектуры с небольшой функцией.
- Публикация автоматическая (DEC-010): каждый commit в `main`, прошедший `npm test` в GitHub Actions, выкатывается на https://rasputye.vercel.app. Значит, мёрж в `main` — это публикация; мёржит владелец проекта или назначенный им интегратор. Агенты не запускают ручной deploy в обход CI, даже при доступе к Vercel. Sites больше не обновляется. Прямые записи в `main` для координации статуса тоже уходят в публикацию, поэтому они не трогают `dist/`.
- CI настроен в `.github/workflows/deploy.yml`: тесты на каждый push и PR, deploy только из `main`. Автоматическая защита `main` и блокировки задач НЕ настроены. Не утверждайте обратное. Прямые записи в `main` разрешены только для координации статуса выше и первичной установки этого пакета документов; дальнейшие изменения правил — через PR.

## Контракты продукта и данных

- Название интерфейса — «Распутье», редакция — D&D 5e 2014. Имя репозитория `YGXVI/tavern` и исторические ключи хранилища менять без миграции нельзя.
- Игрок и мастер — роли в конкретной кампании, не глобальные типы аккаунта. Политики будущей серверной модели описаны в `docs/data.md`; она ещё не реализована.
- Текущий выбор роли — локальный демонстрационный режим, не авторизация. Не выдавайте скрытую кнопку или функцию `isMaster` за защиту данных.
- Не сохраняйте секреты, пароли и реальные аудиозаписи в репозитории, логах или документации. Не добавляйте платные интеграции и не расширяйте доступ приложений без задания пользователя.
- Не подменяйте весь `dist/` сгенерированной версией из другой ветки. Сохраняйте существующие DOM ID, ключи и форматы, пока их замена не согласована.

## Проверки и завершение

- Проект сейчас buildless: JS-модули и CSS в `dist/` являются исходниками. `npm run dev` запускает Python HTTP server на 4173; `npm test` — Node test runner. Не добавляйте сборщик только ради документации.
- Для кода: выполните `npm test`, проверку синтаксиса изменённых JS и уместную проверку сценария в браузере. Для документации: проверьте ссылки, пути и соответствие коду. Не пишите тесты, лишь повторяющие реализацию.
- Визуальные изменения проверяйте на узком экране, в светлой и тёмной теме. Для входа/ролей проверяйте оба режима. Отсутствующую проверку называйте отсутствующей.
- Обновите спецификацию функции, статус и журнал решений, если изменён контракт. Различайте «локально готово», «PR готов», «в main» и «опубликовано».
- В конце передайте: задачу и исполнителя, ветку/PR/commit, изменённые файлы, что проверено, ограничения и следующий шаг. Нельзя обещать, что коллега уже прочитал документы или что интеграция подключена, без подтверждения.
