# Распутье: общие правила для людей, Codex и Claude Code

Все участники равны по процессу: одинаковые правила планирования, review и интеграции. Новая просьба одного участника не отменяет общие договорённости автоматически. Изменения процесса и исключения согласуют затронутые участники с записью в Issue/PR; роль владельца репозитория не даёт приоритета в рабочих решениях. `CLAUDE.md` подключает этот файл. OpenSpec описывает изменения; GitHub хранит договорённости участников. Автоматических блокировок задач нет.

## Перед началом

Прочитать [процесс OpenSpec](docs/open-spec.md), [видение](docs/vision.md), [статус](docs/status.md), [решения](docs/decisions.md), [контракт данных](docs/data.md), [словарь](docs/glossary.md), затронутые `openspec/specs/*/spec.md`, активные changes, свежий `main`, Issues и PR. `openspec/specs/` описывает текущее поведение; будущая работа — в changes и явно помеченных планах. Старые `docs/features/*.md` — указатели.

## Ответственность и параллельная работа

- Новая задача: один `TASK-ID`, один change `task-ID-slug`, одна опубликованная GitHub Issue, один ответственный человек с указанием агента/сессии. Номер Issue и TASK-ID — разные идентификаторы; ID сверять с Issues и старой таблицей. Не назначать коллег без согласия.
- До кода опубликовать заявку через шаблон Issue: исполнитель, проверяющий, интегратор, ветка, полный SHA базы, файлы/контракты, зависимости, ссылка на change/PR и время с часовым поясом. Проверяющий должен подтвердить план в Issue или PR; исполнитель не утверждает свой план за коллегу. До подтверждения можно готовить план. Заявка считается согласованной после проверки пересечений. При споре затронутые участники согласуют решение; пока соглашения нет, спорная часть остаётся blocked, независимая работа продолжается.
- У каждого отдельный checkout/worktree; работа ведётся в постоянной ветке направления из [реестра](docs/workstreams.md), например `codex/network`, `codex/rules5e`, `codex/voice`, `claude/dev`, `codex/process`. Ветка переиспользуется между задачами; TASK-ID и имя агента не требуют новой ветки. В одной ветке одновременно один активный исполнитель и один открытый PR в main; передачу исполнителя фиксировать явно. Префикс codex/claude — часть исторического имени, не привилегия инструмента или человека. Одна папка change — один автор. Общие файлы, API, схемы, DOM, хранилище и глобальные CSS требуют согласованного владельца/порядка интеграции. Разные папки changes не устраняют конфликты кода.
- После согласования `proposal.md`, delta specs, `design.md`, `tasks.md` выполнять реализацию. При смене объёма обновить план и получить подтверждение затронутых участников до изменения новых общих файлов. Мелкую опечатку без изменения поведения можно оформить коротким PR без change; указать основание.
- Статусы новых задач вести в Issue: `proposed → reserved → in_progress → review → done`, дополнительно `blocked/paused`. `done` — после интеграции и проверки. Публикацию подтверждать отдельно по Actions. Не снимать чужую задачу по давности, не обещать, что коллега прочитал инструкции.
- Завершённые заявки и старые task-ветки сохраняются как история. Активную работу переводить на ветку направления по согласованию с её исполнителем, без сброса/переименования чужой копии и переписывания готовых PR. Новые зависимости — отдельные Issues/changes, а не обязательные новые ветки. Если запись в GitHub недоступна, готовить локальный дифф и сообщать о блокере; резервирование не состоялось.

## Интеграция и проверки

- Код, правила, specs и конфигурация — через PR. Новые заявки публикуются в Issues; прямой push в main не заменяет PR и review. Архивные разовые разрешения и частные исключения, включая самостоятельный merge из DEC-013, не отменяют действующий единый процесс (DEC-015).
- Автор передаёт конкретную ревизию PR другому участнику на review. Интегратором для PR может быть любой согласованный участник с техническим доступом, включая проверяющего; специального назначения владельцем не требуется. Автор не подтверждает свой review и не объединяет собственный PR вместо коллеги. Интегрировать по одному PR, начиная с зависимостей. Перед merge учесть свежий `main`, согласовать пересечения и повторить затронутые проверки. Ветки направлений синхронизировать обычным merge из main перед новой порцией и после её интеграции; для повторных PR использовать merge commit, без squash/rebase общей истории. Не удалять ветку после задачи автоматически. PR содержит небольшую законченную порцию; не накапливать несвязанные задачи и не добавлять новый объём во время финального review.
- Перед PR: `npm ci`, `npm run spec:validate`, `npm run spec:validate:archive`, `npm test`; для изменённого JS — синтаксис, для поведения — соответствующий сценарий браузера. UI — узкий экран и доступные темы/роли; четыре темы существуют только в `/legacy/`. Отсутствующие проверки назвать отсутствующими.
- Перед финальным review синхронизировать delta specs и архивировать change в своей ветке только после выполнения задач и проверки. Архивация — обновление документов, не merge/deploy. Невлитые PR не становятся частью поведения `main`. После новых замечаний повторно открыть change или создать последующее изменение, не подделывать завершение.
- PR содержит Issue/TASK/change, результат, зависимости, файлы/контракты, проверки, ограничения, миграцию и откат. Общие решения добавлять с новым DEC-ID, чужую историю сохранять.
- `main` с зелёными тестами и проверкой OpenSpec автоматически публикуется на Vercel (DEC-010). Ручной deploy в обход CI и обновление Sites не выполнять. Эти правила не настраивают GitHub branch protection: фактические ограничения проверить отдельно; без технической защиты соблюдение PR/review остаётся договорённостью. Административный доступ не даёт исключения из процесса.

## Контракты и общие файлы

- «Распутье», D&D 5e 2014; `YGXVI/tavern` и исторические ключи не переименовывать без миграции. Роль относится к кампании; скрытие UI не защищает секреты. Песочницу и серверный режим различать по актуальным `docs/data.md`, решениям и коду; не объявлять план реализованной авторизацией.
- `dist/` — исходники buildless-приложения. Новый стол: `dist/js/**`, `dist/css/**`, `dist/index.html`; старый прототип: `dist/legacy/**`. Не вводить сборщик/платформу попутно.
- `dist/js/core/store.js`, `campaign.js`, `auth.js`, `dist/engine.js`, `dist/js/main.js`, глобальный CSS и `dist/index.html` — общие контракты. Их меняет согласованный исполнитель; ключи/форматы — вместе с `docs/data.md`, specs и решением. `package.json`, lockfile и CI также имеют одного владельца на изменение.
- Не выполнять `reset --hard`, `clean`, force-push, переписывание общей истории или замену всего `dist/` чужой генерацией. При конфликте сохранить смысл обеих работ.
- Секреты, пароли, токены и реальные аудиозаписи не помещать в Git/логи. Платные интеграции, источники контента и расширение доступа требуют отдельного задания.
- Итог передачи: исполнитель, TASK/Issue/change, ветка/PR/commit, проверки, ограничения и следующий шаг. Центральный чат помогает отслеживать состояние и не имеет особых полномочий; опубликованные документы и GitHub — общая память команды.
