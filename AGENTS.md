# Распутье: общие правила для людей, Codex и Claude Code

Это канонический текст процесса. `CLAUDE.md` подключает его; [OpenSpec](docs/open-spec.md) содержит работу с change и команды, [реестр](docs/workstreams.md) — ветки и хозяев, DEC-015 и DEC-016 — решения и причины. Участники равны: владелец аккаунта, центральный чат и агент не дают процессных привилегий. Изменения правил согласуют затронутые люди.

## Перед началом

Прочитать этот файл, [видение](docs/vision.md), [данные](docs/data.md), [решения](docs/decisions.md), [словарь](docs/glossary.md), [реестр](docs/workstreams.md), затронутые specs/changes, свежий main и Issues/PR. docs/status.md — обзор и ссылки, не второй источник статусов. Текущее поведение и планы различать по ревизии Git.

## Задачи и направления

- У задачи одна опубликованная Issue и один ответственный человек с указанием агента/сессии. Для новых задач после принятия этой редакции TASK-NNN равен номеру Issue: #73 → TASK-073. Сначала создать Issue, затем добавить номер в заголовок; при необходимости change назвать task-073-slug. Номер выдаёт GitHub; task:next не нужен. В Issue указать уровень, направление, исполнителя, хозяина, проверяющего, интегратора, полный SHA базы, файлы/контракты, зависимости и время с часовым поясом. Неизвестные роли оставить неназначенными.
- Существующие до перехода задачи сохраняют исторические соответствия TASK↔Issue (TASK-036 → #60), включая уже заведённые TASK-037…045. Коммиты и историю не переписывать. Ошибочный второй TASK-036 в #63 исправляется отдельно его исполнителем; #60 остаётся за процессом. Наличие Issue само по себе не подтверждает согласование.
- Хозяин направления назначается только с согласия людей и записывается в реестре. Он решает внутри направления; пересечения общих контрактов решают затронутые участники. Владение направлением не отменяет требования уровня. При споре blocked только спорная часть, независимая работа продолжается.
- Один активный исполнитель на постоянную ветку, каждый в собственном checkout/worktree. Второму автору нужна явная передача. Одна папка change — один автор. Префиксы веток и имя агента людей не назначают.

## Уровни изменений

Для смешанного PR действует самый высокий затронутый уровень; разделение одного изменения общего контракта не снижает уровень.

| Уровень | Область | Артефакты и согласование | Review и merge |
| --- | --- | --- | --- |
| L0 | Небольшая правка внутри направления без нового поведения, общих контрактов, формата данных, SQL и зависимостей; исправление существующих записей без смены формата | Issue и PR; change не обязателен, основание указать | Зелёный CI; автор может объединить сам. Для интерфейса — одобрение по DEC-016 ниже |
| L1 | Новое поведение внутри направления без L2; импорт новых записей в прежнюю схему из согласованного источника | Issue, change и PR; предварительное подтверждение плана не нужно | Review другого участника после реализации; допустим агент другого человека. Самостоятельный merge — по таймауту ниже либо по исключению интерфейса DEC-016 |
| L2 | Общие API/DOM/CSS/хранилище, схема/формат/ключи данных и docs/data.md, миграции, SQL/RLS, package.json/lockfile, CI, процесс, новый внешний источник контента и его лицензия | Issue, change и PR; другой затронутый человек явно подтверждает конкретную ревизию плана до реализации | Человеческий review результата и согласованный интегратор с доступом, кроме автора PR; таймаута нет |

Для L0–L1 независимый проверяющий — другой человек или агент другого человека (Codex ↔ Claude), не другой агент того же автора. Агент не выдаёт заключение за человеческое согласие L2. Review указывает человека/агента, SHA, область и результат; автор не подтверждает себя, кроме явно согласованного исключения интерфейса DEC-016. Для L2 до подтверждения можно исследовать и готовить план. Уже полученное согласование внутри того же объёма повторно не запрашивать; существенная смена области/контрактов требует нового подтверждения.

## Интерфейс: одобрение sol0139 (DEC-016)

- Хозяин интерфейса — sol0139, постоянная ветка `claude/dev`. Только для L0–L1 целиком внутри интерфейсной границы реестра sol0139 одобряет результат и может объединять PR, включая собственные и подготовленные его агентом, после зелёного CI и обязательных проверок. Его одобрение и merge не нарушают DEC-015; ждать независимого review или 24 часов не нужно. Обязательное независимое review после такого merge не вводится; полученные замечания и дефекты всё равно закрываются исправлением или revert.
- Одобрение sol0139 фиксируется в Issue/PR с полным SHA и областью. Агент может выполнить merge по этому одобрению, но не выдаёт собственное заключение или молчание за решение sol0139. Содержательное изменение SHA требует нового одобрения. Открытые блокирующие замечания и споры сохраняют силу.
- Явный запрос одобрения в Issue/PR указывает sol0139, полный SHA, область и время с часовым поясом. Если ответа нет в течение часа, автор обращается к Яре (YGXVI) там же со ссылкой на запрос. Яра может явно одобрить указанную ревизию или потребовать исправления/review. Час молчания не означает одобрения; автоматического merge и обхода через общий таймаут L1 нет.
- Любое L2 и изменение общего контракта, даже внутри UI-файла или интерфейсной spec/change, остаётся по общим правилам: план и результат подтверждает другой затронутый человек; автор PR не интегрирует его сам. Смешанный PR наследует высший уровень. Другие направления этим исключением полномочий не получают.

## Уведомления и 24 часа

- Для пересечений L0–L1 явно уведомить затронутого участника в Issue/PR: адресат, область, запрос, время. Через 24 часа без ответа это отсутствие возражений только по заявленному пересечению. Существенная смена объёма требует нового уведомления и перезапуска срока. Уже заявленные возражения таймаут не отменяет.
- Для L1 вне исключения интерфейса DEC-016 отдельный явный запрос review конкретного SHA запускает срок review. Если за 24 часа review не получено, CI зелёный, обязательные проверки выполнены и нет открытых блокирующих замечаний/споров, автор может влить сам. Он фиксирует запрос, срок, SHA, CI и основание merge; отсутствие review не называет одобрением. Содержательная смена SHA требует нового запроса; исправления после review проверяются на новом SHA.
- Review L1 после такого merge остаётся обязательным: запрос и отсутствие review сохраняются в Issue до проверки при следующей доступной сессии другой стороны. Замечания закрываются исправлением или revert. Статус published не закрывает дефекты и обязанность review.
- Для L2 молчание не означает согласия по плану или review; выхода через 24 часа нет.

## PR из постоянных направлений и интеграция

- Работать в существующей постоянной ветке из реестра и открывать PR непосредственно из неё в main. Новые ветки по TASK, плану или review, включая `<направление>-review-task-NNN`, не создавать. Новое постоянное направление требует согласования затронутых людей; имя ветки не заменяет этого согласования.
- Один открытый интеграционный PR на направление. Он содержит задачу или связанную пачку с перечисленными TASK/Issues/changes, зависимостями и полным проверяемым SHA. Незавершённый объём публиковать как draft/WIP и не выдавать за готовый к merge.
- Пока PR ожидает окончательного review, не добавлять в его ветку новые посторонние задачи. Можно исследовать и готовить независимые планы вне проверяемого diff; одна постоянная ветка не даёт независимых выпусков нескольких ревизий. Координатор согласует очередь и границы порции без создания task/review-веток. Исправления замечаний и необходимый merge свежего main публикуются в той же ветке с новым SHA и повтором затронутых проверок. Одобрение старого SHA не распространяется автоматически на новую содержательную ревизию.
- Перед merge учесть свежий main, пересечения и повторить затронутые проверки. Использовать обычный merge commit, без squash/rebase общей истории. После интеграции включить main обычным merge в ветку направления; постоянную ветку автоматически не удалять.
- Существующие task/plan/review-ветки не удалять и не переносить автоматически: сначала проверить полный HEAD, уникальные коммиты, открытые PR и занятость рабочих копий; сохранить невлитую работу в согласованном постоянном направлении. Старый PR заменять только после создания и проверки ссылки на новый PR. Удаление безопасных старых refs — отдельная координируемая работа; исторические решения/архивы сохраняются (DEC-017).
- Код, данные, правила и конфигурация — через PR; прямой push main не заменяет процесс. Самостоятельный merge разрешён L0, L1 по таймауту либо для интерфейса L0–L1 с одобрением по DEC-016. Старые частные разрешения не отменяют классификацию (DEC-015).

## Проверки и статусы

- Перед PR: npm ci, npm run spec:validate, npm run spec:validate:archive, npm test; изменённый JS — синтаксис, поведение — соответствующий сценарий. UI — узкий экран, доступные темы/роли (четыре темы только в /legacy/). Документы — ссылки, пути и соответствие коду. Не повторять незатронутые проверки без причины; отсутствующие назвать явно.
- Завершённый change синхронизировать со specs и архивировать в ветке после проверок перед финальным review. После замечаний повторно открыть либо оформить последующее изменение. Архив/галочки не доказывают review, merge или deploy. Незавершённый план не архивировать как реализованное поведение.
- Единственная шкала Issue: proposed → reserved → in_progress → review → merged → published; дополнительно blocked/paused. reserved — согласованы исполнитель/границы по уровню; merged — подтверждён merge SHA; published — успешный deploy по Actions. Для изменений без deploy конечный статус merged. done в новых задачах не использовать; исторические записи трактовать по их доказательствам, не переписывать. После таймаута L1 статус merged/published возможен при отдельной незакрытой обязанности review.
- Статус, подтверждения, PR/commit, проверки и следующий шаг — в Issue. Не снимать чужую задачу по давности и не менять ответственного без передачи. При недоступном GitHub сообщить блокер и готовить локальный план/дифф, не объявляя резервирование состоявшимся.
- main с зелёными проверками автоматически публикуется на Vercel. Ручной deploy в обход CI и обновление Sites не выполнять. Защита main (запрет force-push/удаления, обязательный CI, без обязательных GitHub approvals) согласована как отдельная административная работа; этот PR её не включает и не подтверждает настройку. Проверка TASK↔Issue — следующая отдельная задача CI, ещё не реализована; исторические соответствия обязательны.

## Контракты продукта и сохранность работы

- «Распутье», D&D 5e 2014; YGXVI/tavern и исторические ключи не переименовывать без миграции. Роль относится к кампании. Песочницу/сервер различать по docs/data.md и коду; скрытие UI не защищает секреты.
- dist/ — исходники buildless-приложения: новый стол dist/js/**, dist/css/**, dist/index.html; прототип dist/legacy/**. Не вводить сборщик/платформу попутно.
- Общие контракты: dist/js/core/store.js, campaign.js, auth.js, dist/engine.js, dist/js/main.js, глобальный CSS, dist/index.html, схема данных, package.json/lockfile и CI. Менять с согласованным владельцем/порядком; формат хранилища — вместе с docs/data.md и миграцией. Уровень определяется затронутым контрактом, а не только путём; косметическая правка файла не равна изменению глобального поведения.
- Не выполнять reset --hard, clean, force-push, переписывание общей истории или замену всего dist/ чужой генерацией. При конфликте сохранить смысл обеих работ. Не помещать секреты/реальные записи сессий в Git/логи. Платные интеграции и расширение доступа требуют отдельного задания.
- Передача: человек/агент, TASK/Issue, уровень/change, постоянная ветка/PR/commit, review или основание таймаута, проверки, merge/deploy, ограничения и следующий шаг. Общение агентов не заменяет согласие людей L2; автоматический обмен сообщениями и запуск агентов этим документом не настроены.
