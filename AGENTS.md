# Распутье: правила работы для людей, Codex и Claude

Канонический текст процесса по распоряжению YGXVI от 04.11.2026 ([DEC-018](docs/decisions.md)). `CLAUDE.md` подключает его. Направления, ветки и ответственные — в [реестре](docs/workstreams.md). Цель правил — короткий путь от задачи до результата:

**получил задачу → написал код → проверил → влил в `test` → исправил найденное.**

Владелец (YGXVI) подключается к существенным решениям и к выпуску проверенной версии в `main`.

## Перед началом

Читать только то, что относится к задаче: этот файл, Issue своего направления, затронутый код и specs, свежие `test` и `main`. Повторный аудит всего проекта при каждом поручении не нужен. Справочно: [видение](docs/vision.md), [данные](docs/data.md), [решения](docs/decisions.md), [словарь](docs/glossary.md).

## Ветки: рабочая → `test` → `main`

- **Рабочие ветки направлений** перечислены в реестре. Имя ветки не называет человека или инструмент и хозяев не назначает. Ветки повторно не переименовывать. Новых веток под отдельную задачу, план или review не создавать.
- **`test`** — общая интеграционная ветка команды. Без дополнительного подтверждения YGXVI агент может: переносить туда готовые изменения своего направления, делать merge, разрешать обычные конфликты, запускать интеграционные и регрессионные тесты, исправлять найденные ошибки, повторять интеграцию, собирать тестовые сборки, откатывать собственные неудачные изменения revert-коммитом. Отдельные Issue, OpenSpec, согласование архитектуры и одобрение PR для этого не нужны. Если GitHub позволяет — прямой merge и push без PR; если PR нужен технически — короткий, без многоступенчатого review.
- Перед интеграцией обновить свою ветку свежим `test` обычным merge. Конфликт с чужой работой, который нельзя разрешить без изменения её поведения, согласовать с её исполнителем в Issue направления.
- `test` может временно содержать ошибки — она для того, чтобы находить их до выпуска.
- **`main`** — защищённая стабильная ветка. Прямой push и merge мимо проверки запрещены. Источник — проверенная `test` или проверенный выпускной коммит из неё. Перед выпуском: сборка, тесты и критические сценарии в браузере (вход, кампания, стол: токены, рисование, бой; лист). Заведомо нестабильное не выпускать; если в `test` есть незавершённые функции, сначала выделить проверенный набор. **Выпуск в `main` — только с разрешения YGXVI** (PR из `test` или выпускного коммита). `main` с зелёными тестами выкатывается на Vercel сам; ручной deploy в обход CI не выполнять.
- Запрещено: force-push, переписывание общей истории (rebase/squash общих веток, reset общих refs), потеря чужих коммитов, разрушительные изменения общих данных, production-секреты на тестовом стенде.

## Задачи: одна Issue — одно направление

- Направление ведётся одной Issue: цель, ответственный, статус, сделанное, незавершённое с чекбоксами, решения и ограничения, зависимости, ссылки на старые Issues и активные PR, следующая конкретная задача. Карточку актуализировать правкой тела, а не серией комментариев.
- **Новая Issue — исключение.** Допустима только для самостоятельной крупной функциональности вне существующих направлений, отдельного критического дефекта или работы с отдельным исполнителем, результатом и жизненным циклом. Не создавать Issue ради согласования, технического вопроса, отчёта, небольшого исправления, нового этапа, передачи между агентами, обсуждения архитектуры, review, планирования, документации или повторного исследования принятого решения. Сомневаешься — используй существующую.
- Вопросы агентов друг к другу — прямо в Issue или PR направления, не отдельными задачами.
- Старые номера TASK-NNN = номер Issue остаются в истории, коммитах и архиве OpenSpec; новые этапы — пункты чек-листа Issue направления.

## Согласования

- **Утверждение задачи — разрешение довести её до работающего результата**, включая обычные технические решения. Детали реализации агент выбирает сам, если не меняет утверждённые требования и не создаёт значимого риска.
- Повторно не согласовывать: утверждённую архитектуру и функционал, назначенного исполнителя, выбранное направление, следующий этап утверждённой цели, обычное исправление ошибки, запуск тестов, интеграцию в `test`.
- Отдельное решение нужно только для: фундаментальной смены архитектуры, изменения модели безопасности, разрушительной миграции данных, новых расходов, изменения полномочий и доступа, выпуска в `main`. Тогда запросить **одно конкретное решение с рекомендуемым вариантом**, без многоэтапного обсуждения.
- Повторный review неизменённого кода не проводится. Агенты одного человека не являются друг для друга независимыми проверяющими.
- OpenSpec — когда помогает зафиксировать сложное изменение ([open-spec.md](docs/open-spec.md)); обязательного пакета документов для небольшой реализации нет.

## Агенты и координация

- Агенты, уполномоченные одним человеком, действуют от его имени; ответственность — у этого человека. Claude и Codex могут продолжать работу друг друга без переоформления задач: перед продолжением проверить полный SHA, состояние рабочей копии и открытые PR. Одновременная запись двух исполнителей в одну ветку запрещена; при параллельной работе договориться о конкретных файлах и коммитах.
- Подпись агента содержит человека: «YGXVI / Claude», «sol0139 / Claude Code», «Dezmondy / Claude». Комментарий агента не подменяет решение человека.
- Центральный агент отслеживает приоритеты и состояние интеграции, но не согласует каждый коммит. Управленческих уровней между исполнителем и результатом не добавлять.

## Отчёт

Короткий, в Issue или PR направления:

```
Done / Tests / Branch / SHA / Next
Blocked / Причина / Что требуется
```

Многостраничные комментарии — только по прямому запросу владельца.

## Проверки

Перед интеграцией в `test`: `npm ci` (если менялись зависимости), `npm run spec:validate`, `npm run spec:validate:archive`, `npm test`; изменённый JS — `node --check`; поведение — сценарий в браузере, для интерфейса и узкий экран. Что не проверено — назвать в отчёте.

## Продукт, данные и безопасность

- «Распутье», D&D 5e 2014. `dist/` — исходники buildless-приложения (новый стол `dist/js/**`, `dist/css/**`, `dist/index.html`; прототип `dist/legacy/**`). Сборщик и платформу попутно не вводить.
- Общие контракты — `dist/js/core/store.js`, `campaign.js`, `auth.js`, `dist/js/main.js`, `dist/engine.js`, `dist/index.html`, глобальный CSS, `dist/js/server/**`, `supabase/**`, схема и формат данных с `docs/data.md`, `package.json`/lockfile, CI. Меняя их, проверить затронутые направления и предупредить их ответственных в Issue; формат хранилища менять вместе с `docs/data.md` и миграцией.
- Миграции живой базы — только после бэкапа с проверкой восстановления; разрушительная миграция — отдельное решение владельца.
- Секреты, service role, токены и реальные записи голосов — никогда в Git, логи и браузер. Платные сервисы и расширение доступа — отдельное решение владельца.
- При конфликте сохранять смысл обеих работ; чужую работу не заменять своей генерацией целиком.
