# Распутье: общие правила для людей, Codex и Claude Code

Прямое задание владельца имеет приоритет. `CLAUDE.md` подключает этот файл. OpenSpec описывает изменения; GitHub хранит договорённости участников. Автоматических блокировок задач нет.

## Перед началом

Прочитать [процесс OpenSpec](docs/open-spec.md), [видение](docs/vision.md), [статус](docs/status.md), [решения](docs/decisions.md), [контракт данных](docs/data.md), [словарь](docs/glossary.md), затронутые `openspec/specs/*/spec.md`, активные changes, свежий `main`, Issues и PR. `openspec/specs/` описывает текущее поведение; будущая работа — в changes и явно помеченных планах. Старые `docs/features/*.md` — указатели.

## Ответственность и параллельная работа

- Новая задача: один `TASK-ID`, один change `task-ID-slug`, одна опубликованная GitHub Issue, один ответственный человек с указанием агента/сессии. Номер Issue и TASK-ID — разные идентификаторы; ID сверять с Issues и старой таблицей. Не назначать коллег без согласия.
- До кода опубликовать заявку через шаблон Issue: исполнитель, проверяющий, интегратор, ветка, полный SHA базы, файлы/контракты, зависимости, ссылка на change/PR и время с часовым поясом. Проверяющий должен подтвердить план в Issue или PR; исполнитель не утверждает свой план за коллегу. До подтверждения можно готовить план. Заявка считается согласованной после проверки пересечений; при споре решает владелец.
- У каждого отдельный checkout/worktree, ветка `codex/<task-id>-<slug>` или `claude/<task-id>-<slug>`. Одна папка change — один автор. Общие файлы, API, схемы, DOM, хранилище и глобальные CSS требуют согласованного владельца/порядка интеграции. Разные папки changes не устраняют конфликты кода.
- После согласования `proposal.md`, delta specs, `design.md`, `tasks.md` выполнять реализацию. При смене объёма обновить план и получить подтверждение затронутых участников до изменения новых общих файлов. Мелкую опечатку без изменения поведения можно оформить коротким PR без change; указать основание.
- Статусы новых задач вести в Issue: `proposed → reserved → in_progress → review → done`, дополнительно `blocked/paused`. `done` — после интеграции и проверки. Публикацию подтверждать отдельно по Actions. Не снимать чужую задачу по давности, не обещать, что коллега прочитал инструкции.
- TASK-006–009 завершаются по прежним заявкам `docs/status.md`; сохранять владельцев, ветки и историю. Новые зависимости — отдельные Issues/changes. Не требовать переписывания готовых PR. Если запись в GitHub недоступна, готовить локальный дифф и сообщать о блокере; резервирование не состоялось.

## Интеграция и проверки

- Код, правила, specs и конфигурация — через PR. Новые заявки публикуются в Issues, прямой записью в `main` их больше не резервировать. Исторические TASK-006–009 могут обновлять только свою строку статуса по старому порядку до завершения.
- Автор передаёт PR другому участнику на review; объединяет владелец или явно назначенный им интегратор по одному, начиная с зависимостей. Не мержить свой PR автоматически. Перед merge учесть свежий `main`, согласовать пересечения и повторить затронутые проверки.
- Перед PR: `npm ci`, `npm run spec:validate`, `npm run spec:validate:archive`, `npm test`; для изменённого JS — синтаксис, для поведения — соответствующий сценарий браузера. UI — узкий экран и доступные темы/роли; четыре темы существуют только в `/legacy/`. Отсутствующие проверки назвать отсутствующими.
- Перед финальным review синхронизировать delta specs и архивировать change в своей ветке только после выполнения задач и проверки. Архивация — обновление документов, не merge/deploy. Невлитые PR не становятся частью поведения `main`. После новых замечаний повторно открыть change или создать последующее изменение, не подделывать завершение.
- PR содержит Issue/TASK/change, результат, зависимости, файлы/контракты, проверки, ограничения, миграцию и откат. Общие решения добавлять с новым DEC-ID, чужую историю сохранять.
- `main` с зелёными тестами и проверкой OpenSpec автоматически публикуется на Vercel (DEC-010). Ручной deploy в обход CI и обновление Sites не выполнять. Защита ветки не включается этим пакетом: пока её не настроил владелец, проверки не запрещают прямой push технически.

## Контракты и общие файлы

- «Распутье», D&D 5e 2014; `YGXVI/tavern` и исторические ключи не переименовывать без миграции. Вход через Discord — локальная имитация, не OAuth; роль относится к кампании, UI не защищает секреты. Серверная архитектура остаётся открытым DEC-008.
- `dist/` — исходники buildless-приложения. Новый стол: `dist/js/**`, `dist/css/**`, `dist/index.html`; старый прототип: `dist/legacy/**`. Не вводить сборщик/платформу попутно.
- `dist/js/core/store.js`, `campaign.js`, `auth.js`, `dist/engine.js`, `dist/js/main.js`, глобальный CSS и `dist/index.html` — общие контракты. Их меняет согласованный исполнитель; ключи/форматы — вместе с `docs/data.md`, specs и решением. `package.json`, lockfile и CI также имеют одного владельца на изменение.
- Не выполнять `reset --hard`, `clean`, force-push, переписывание общей истории или замену всего `dist/` чужой генерацией. При конфликте сохранить смысл обеих работ.
- Секреты, пароли, токены и реальные аудиозаписи не помещать в Git/логи. Платные интеграции, источники контента и расширение доступа требуют отдельного задания.
- Итог передачи: исполнитель, TASK/Issue/change, ветка/PR/commit, проверки, ограничения и следующий шаг. Центральный чат помогает отслеживать состояние; опубликованные документы и GitHub — общая память команды.
