# OpenSpec: единый процесс команды

## Равные участники

У всех одинаковые правила. Автор, проверяющий и интегратор — роли конкретного изменения; они не закреплены за владельцем репозитория, агентом или центральным чатом. Роли принимаются с согласия людей. Один участник не отменяет договорённости прямым указанием; изменение процесса и исключение обсуждают затронутые участники и фиксируют в Issue/PR. Спорная часть остаётся blocked до соглашения, остальные независимые работы продолжаются.

Проверяющий — другой участник; интегратором может быть он же или другой согласованный участник с доступом. Автор не утверждает собственный review и не заменяет коллегу при merge. Этот порядок одинаков для всех направлений, включая claude/dev. Исторические исключения описывают прошлое, действующий порядок — DEC-015.

## Где хранится состояние

- GitHub Issue: TASK-ID, ответственный, ветка направления, статус, пересечения и зависимости. Номер Issue не равен TASK-ID.
- openspec/specs: текущее согласованное поведение в соответствующей Git-ревизии.
- openspec/changes: предложения и незавершённая работа; после завершения — archive.
- docs/decisions.md: решения и причины; история сохраняется, отменённый порядок замещается новым DEC-ID.
- docs/status.md: обзор и ссылки, а не второй конкурирующий список статусов новых задач.
- Центральный чат: сводка и координация без права односторонне менять процесс или давать подтверждение за коллег.

## Установка и актуализация

Нужен Node.js >=20.19.0 (CI — 22), OpenSpec 1.15.0 закреплён в devDependencies/lockfile. Глобальная установка не нужна. В чистой собственной копии обновить main (`git pull --ff-only origin main`), затем `npm ci`, `npm run openspec -- --version`, `npm run spec:validate`, `npm test`. Сначала сохранить незавершённую работу в своей ветке; не сбрасывать её и не переключать чужую копию.

Проектные интеграции Codex (.agents/skills/openspec-*) и Claude Code (.claude/skills и commands/opsx) уже в Git. Открыть новую сессию агента в своей копии. Если файлов нет — npm run spec:setup, проверить diff; не обновлять CLI или глобальные настройки попутно. Начинать с AGENTS.md, этого документа, docs/workstreams.md, видения/данных/решений, затронутых specs и свежих Issues/PR.

## Ветки по направлениям

Постоянная ветка выбирается из [реестра](workstreams.md): например codex/network, codex/rules5e, codex/voice, claude/dev, codex/process. TASK-ID и change отдельные для каждой задачи, но новая ветка на задачу не требуется. Каждый агент работает в собственной копии; на одну ветку — один активный исполнитель и один открытый PR в main. Префикс имени не ограничивает передачу другому инструменту или человеку.

Перед новой порцией: fetch и обычный merge свежего main в ветку направления. Изменения коммитить по задачам. После merge PR — снова подтянуть main и продолжить в той же ветке. Использовать merge commit, не squash/rebase общей истории; ветку направления не удалять автоматически. Готовые старые PR не переписывать ради переименования.

## Порядок задачи

1. Проверить актуальные main, Issues, PR и границы направлений. Опубликовать Issue: свободный TASK-ID, change, направление/ветка, исполнитель, проверяющий, интегратор, полный базовый SHA main, файлы/контракты, зависимости, дата/время с часовым поясом. Не назначать людей без согласия.
2. Проверить пересечения файлов, API, DOM, CSS, данных. Явно записать отсутствие пересечений или порядок общего изменения. Это соглашение, не техническая блокировка; постоянные ветки также могут конфликтовать.
3. Подготовить proposal, specs, design, tasks; change называть task-ID-slug. Другой участник подтверждает конкретную ревизию плана в Issue/PR до реализации. До подтверждения готовить план можно. Для опечатки без изменения поведения достаточно короткого PR с основанием отсутствия change.
4. Реализовать согласованный объём. Не запрашивать повторно уже полученное согласование для каждого шага внутри этого объёма; при изменении общих контрактов/области обновить план и согласование. В одной ветке не добавлять новую независимую задачу, пока предыдущая порция ожидает финального review/merge.
5. PR по умолчанию содержит одну завершённую задачу; небольшая связанная пачка допустима с перечнем TASK/Issues/changes и зависимостей. Не накапливать несвязанные функции в большой выпуск. На время финального review зафиксировать head; исправления по review проверяются повторно по затронутому объёму.
6. Выполнить уместные проверки и сопоставить требования со сценариями. Синхронизировать specs и архивировать завершённый change в ветке перед финальным review. Архив и галочки не доказывают merge/deploy. Незавершённый план не архивировать и не объявлять реализованным после merge документации.
7. После подтверждения другим участником и зелёных проверок согласованный интегратор объединяет конкретную ревизию обычным merge, по зависимостям. Источник должен учитывать свежий main; при изменении контракта/области прежнее одобрение не переносить автоматически. Done — после интеграции и проверки; публикация — по успешному Actions. Исполнитель синхронизирует ту же ветку с main для следующей задачи.

Статусы Issue: proposed → reserved → in_progress → review → done; дополнительно blocked/paused. Нельзя снимать чужую задачу по давности или менять ответственного без передачи. При недоступном GitHub подготовить локальный план/дифф, сообщить о блокере и не объявлять резервирование опубликованным.

## Команды

| Действие | Codex: в чате / выбрать skill | Claude Code: в чате |
| --- | --- | --- |
| Исследовать | `$openspec-explore` | `/opsx:explore` |
| Подготовить change | `$openspec-propose task-ID-slug` | `/opsx:propose task-ID-slug` |
| Уточнить план | `$openspec-update-change task-ID-slug` | `/opsx:update task-ID-slug` |
| Реализовать | `$openspec-apply-change task-ID-slug` | `/opsx:apply task-ID-slug` |
| Синхронизировать | `$openspec-sync-specs task-ID-slug` | `/opsx:sync task-ID-slug` |
| Архивировать | `$openspec-archive-change task-ID-slug` | `/opsx:archive task-ID-slug` |

CLI-команды выполняются в терминале, не в чате:

```sh
npm run openspec -- list
npm run openspec -- new change task-ID-slug
npm run openspec -- instructions proposal --change task-ID-slug
npm run openspec -- status --change task-ID-slug
npm run spec:validate
npm run spec:validate:archive
npm test
```

CLI создаёт каркас и выдаёт инструкции; документы заполняют участник/агент. Validate проверяет структуру, не истинность требований, согласие коллег или достаточность тестов. Непроверенные сценарии назвать явно. Runtime/SQL/сеть проверять отдельно по изменению; документы — ссылки, пути и соответствие коду. Не повторять незатронутые проверки без причины. Даты задач указывать с часовым поясом.

## Переход и технический контроль

История TASK-006–009 и старые ветки сохраняются. Участники продолжают текущую работу в существующих ветках направлений; перевод оставшейся task-ветки согласовать с её исполнителем без сброса чужих файлов. Особое разрешение DEC-013 для самостоятельного merge claude/dev заменяется общим peer-процессом DEC-015.

CI перед deploy запускает npm ci, проверки OpenSpec и npm test. Merge main автоматически публикует Vercel; ручной deploy в обход CI не выполнять. Документы не настраивают защиту GitHub и не являются автоматическими блокировками. Настройку обязательных approvals/CI и запрета прямого push команда рассматривает отдельно; участник с административным доступом выполняет согласованные настройки, а не получает особые права в процессе.

Источники: [OpenSpec team workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md), [повторное слияние постоянных веток](https://git-scm.com/docs/gitfaq).
