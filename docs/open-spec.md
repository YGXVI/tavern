# OpenSpec: работа команды из трёх человек

## Установка после получения изменений

Node.js >=20.19.0 (в CI — 22). OpenSpec закреплён в devDependencies и lockfile на **1.15.0**; глобальная установка не нужна. Откройте корень своей рабочей копии репозитория.

Сначала `git status`: незавершённую работу сохранить в своей ветке/commit; не сбрасывать и не переключать чужой checkout. В чистой собственной копии:

```sh
git switch main
git pull --ff-only origin main
npm ci
npm run openspec -- --version
npm run spec:validate
npm test
```

До merge пакета эти команды работают в подготовленной ветке `codex/task-010-openspec`; инструкция получения main применяется после его merge. Изменения подготовлены в отдельной ветке от актуального main; перед публикацией проверить свежие изменения коллег.

В репозитории уже сохранены проектные интеграции: `.agents/skills/openspec-*` для Codex и `.claude/skills/openspec-*`, `.claude/commands/opsx/` для Claude Code. Откройте новую сессию агента **в этой рабочей копии**, чтобы он обнаружил их. Если интеграций нет: `npm run spec:setup`; команда генерирует только проектные интеграции core для обоих инструментов. Проверить `git diff`, не коммитить случайную перегенерацию. Не выполнять глобальное обновление OpenSpec или `init --force` попутно.

## Что читать

1. `AGENTS.md`: общие обязательные правила (`CLAUDE.md` подключает их).
2. Этот документ, `docs/vision.md`, `docs/status.md`, `docs/decisions.md`, `docs/data.md`, `docs/glossary.md`.
3. Спецификации затронутых областей `openspec/specs/*/spec.md`, активные changes, Issues и PR.

Requirements в specs описывает текущее поведение. Перенесённые целевые разделы — планы, а не реализованные функции. Новые договорённости оформлять change. `docs/features/` сохраняет ссылки и не дублирует требования.

## Распределение ролей

На каждом изменении три функции: автор, проверяющий, интегратор. Автор — один конкретный человек и его агент/сессия. Проверяющий — другой человек; он подтверждает план и проверяет результат. Интегратор — владелец проекта либо явно назначенный им участник; может совпадать с проверяющим. Роли не назначаются за человека без согласия. Если проверяющий не определён, change остаётся планом.

Один человек может вести несколько независимых changes, но общие файлы и контракты меняются в согласованном порядке. Центральный чат владельца собирает состояние и выявляет пересечения; он не заменяет опубликованные заявки и не назначается интегратором автоматически.

## Порядок новой задачи

1. Проверить свежий main, открытые Issues/PR и старую таблицу TASK. Выбрать следующий свободный TASK-ID (номер Issue не равен TASK-ID). Создать Issue через «Задача OpenSpec» до кода: change ID, автор, проверяющий, интегратор, база SHA, ветка, файлы/контракты, зависимости, статус и время. В комментариях сохранять историю изменений. Назначение assignee — только с согласием и при наличии доступа.
2. Проверить пересечения. В Issue явно записать результат: «пересечений нет» или согласованного владельца и порядок. Это соглашение, не техническая блокировка. Один автор на папку change. Общие схемы/API/DOM/CSS требуют согласования даже в разных файлах.
3. Создать отдельную ветку от свежего main и собственный checkout. Change называть `task-012-short-name` (пример, не резервирование).
4. Сформировать proposal, delta specs, design, tasks. Создать draft PR с планом или ссылкой на него в Issue, чтобы другой участник мог прочитать файлы до реализации. Он подтверждает конкретную ревизию плана комментарием. Записать ссылку на подтверждение в proposal/Issue. Не ставить подпись за него.
5. После согласования выполнить задачи реализации. Новые общие файлы или изменения контрактов требуют обновить план и согласование. Статус — в Issue; чекбоксы реализации — в tasks.md. Не считать галочки подтверждением тестов, merge или deploy.
6. Выполнить проверки. Сопоставить каждый Scenario с кодом/проверкой; назвать непроверенные сценарии. Синхронизировать delta specs и архивировать change **в ветке** перед финальным review; архив содержит только завершённые задачи реализации/проверки. Merge и deploy — отдельные события Issue. Запрос архивации от CLI не заменяет review коллеги.
7. Интегратор учитывает свежий main, зависимости и результаты проверок, затем объединяет PR. Статус done — после интеграции и проверки; публикация — только по успешному Actions. При замечаниях после архивации возобновить change или оформить последующий, сохраняя историю.

## Команды агента и терминала

| Действие | Codex: в чате / выбрать skill | Claude Code: в чате |
| --- | --- | --- |
| Исследовать | `$openspec-explore` | `/opsx:explore` |
| Подготовить change | `$openspec-propose task-012-short-name` | `/opsx:propose task-012-short-name` |
| Уточнить план | `$openspec-update-change task-012-short-name` | `/opsx:update task-012-short-name` |
| Реализовать | `$openspec-apply-change task-012-short-name` | `/opsx:apply task-012-short-name` |
| Синхронизировать specs | `$openspec-sync-specs task-012-short-name` | `/opsx:sync task-012-short-name` |
| Архивировать | `$openspec-archive-change task-012-short-name` | `/opsx:archive task-012-short-name` |

В Codex desktop можно выбрать соответствующий skill в интерфейсе. Состав команд — core; отдельной команды verify в этом профиле нет. Если агент не обнаружил skill, не имитировать его выполнение: открыть новую сессию, проверить установленные файлы или использовать CLI и читать выданные инструкции.

Терминал (не slash-команды чата):

```sh
npm run openspec -- new change task-012-short-name
npm run openspec -- instructions proposal --change task-012-short-name
npm run openspec -- status --change task-012-short-name
npm run openspec -- list
npm run spec:validate
npm run spec:validate:archive
npm test
```

CLI создаёт каркас и выдаёт инструкции; proposal/specs/design/tasks заполняют человек и агент. `openspec validate` проверяет структуру, а не истинность требований или достаточность тестов. Отдельная сверка сценариев обязательна. Для архивации готового change: `npm run openspec -- archive task-012-short-name` (прочитать предупреждения, не использовать `--no-validate`). Даты архива генерируются CLI; рабочие даты/время в Issue указывать Asia/Dushanbe (+05:00).

## Переход существующих задач

По прямому поручению владельца TASK-006 (PR #2), TASK-008 (PR #4), TASK-009 (PR #5) объединены в main перед OpenSpec; их feature-документы перенесены в openspec/specs. Каталоги и модуль урона доступны в репозитории, но ещё не подключены к UI. TASK-007 (PR #6) уже объединён; его результат — база интерфейсных спецификаций. Новый процесс не меняет статусы чужих задач автоматически. При merge старых PR проверить свежий статус и перенести добавленные ими feature-документы в соответствующие `openspec/specs/`, оставив указатели. Новую реализацию UI и переписывание каталогов не запускать.

`docs/status.md` сохраняет обзор/старые заявки и индекс новых Issues; новый статус имеет один источник — Issue. Для обновления обзорного документа использовать PR. Не нужна новая правка main для каждого резервирования. При невозможности создать Issue явно сообщить о блокере и подготовить локальный план/дифф без заявления, что файлы зарезервированы.

## Что обеспечивает CI

В существующем workflow «Тесты и деплой» перед npm test запускаются npm ci и обе проверки OpenSpec. Deploy зависит от этого job. CI не проверяет согласие людей и не блокирует одновременное редактирование. Защита main и обязательные GitHub approvals не настроены этим пакетом; пока их не включит владелец, порядок соблюдается командой. Документы и tooling не меняют dist, но merge всё равно запускает существующий автодеплой.
