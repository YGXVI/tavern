# Данные и владельцы

## Реализовано: демо-стол v2 (TASK-007, DEC-011)

Источник — `dist/js/**`. Это по-прежнему локальная демонстрация: данные лежат в браузере, сервера, проверки личности и защиты закрытых полей нет. «Онлайн» имитируется между вкладками одного браузера: данные — событием `storage`, мгновенные действия (пинг, перетаскивание, линейка, шаблон, бросок, присутствие) — `BroadcastChannel('rasputye-v2')`.

| Хранилище | Ключ | Форма | Назначение |
| --- | --- | --- | --- |
| localStorage | `rasputye-v2-db` | `{version: 1, rev, users, campaigns}` | Все пользователи-заглушки и кампании. При другом `version` читается как пустое и засевается демо (миграций пока нет). |
| sessionStorage | `rasputye-v2-session` | `{userId, at}` | Кто «вошёл» в этой вкладке: у каждой вкладки свой человек. Не токен. |
| localStorage | `rasputye-v2-last-user` | строка `userId` | Кого подставить в новой вкладке (кроме ссылки-приглашения). |
| sessionStorage | `rasputye-v2-cam:<campaignId>:<sceneId>` | `{x, y, z}` | Камера стола в этой вкладке. |

| localStorage | `rasputye-ref-v1` | `{fav, recent, saved, names}` | Справочник (#203): избранное, недавние, отложенное «в книгу героя». Есть и без входа. |

Старые ключи прототипа (ниже) новый интерфейс не читает и не стирает.

### Схема `rasputye-v2-db` (версия 1)

- `users: {[id]: {id, name, handle, hue, provider: 'discord-demo', createdAt}}` — заглушки «входа через Discord», без токенов и почты.
- `campaigns: {[id]: Campaign}`.
- `Campaign = {id, name, description, cover, level, seats, createdAt, ownerId, status, members, invite, characters, scenes, activeSceneId, combat, paused, log, settings, saveRequests?, portalRequests?, creatures?, book?}`.
- `creatures?: {[id]: CreatureCopy}` (TASK-179, необязательное) — снимки своих существ, поставленных на карту из личной библиотеки: поля `Creature` (раздел «Личная библиотека» ниже) без `updatedAt` и `statblockImage`, с `id` копии (`cc-…`), `sourceId` — id шаблона в библиотеке (только происхождение), `ownerId: null` — копия мастера. Токен такого существа — `monsterId: 'lib:<id копии>'`. Одна копия на шаблон: повторная постановка берёт её же; правка или удаление шаблона копию и токены не меняет. Картинки `library:` в копию не попадают: своя картинка шаблона (#190 E) копируется клиентом в бакет кампании `tokens` (`sb:@tokens/<кампания>/<кто ставит>/<файл>`) — сразу после постановки токен с инициалами получает эту копию, мастер записывает её и в `img` копии существа (повторная постановка берёт её). В песочнице ссылка `idb:` общая и копируется как есть. Нет поля — своих существ в кампании нет.
- `book?` (#203, необязательное) — книга кампании и данные дома кампании, открытые всему отряду: `{notes: [Note], gone: [noteId], next?: {at} | null, session?: {n, startedAt, endedAt|null}, played?, handouts: [Handout]}`. Книга — общий блокнот без глав и сессий: `Note = {id, userId, at, rev, edited?, blocks: [{type: 'h'|'p'|'q', text}]}` — заголовок, текст, цитата; пустые блоки не хранятся, до 40 блоков по 6000 знаков. `gone` — id удалённых заметок (последние 500), чтобы удалённая заметка не вернулась из журнала. Рядом, к блокноту не привязанные: `next` — дата следующей игры, `session` — идёт ли игра, `played` — сколько сессий сыграно (у кампаний до блокнота — по числу старых глав), `Handout = {id, title, text, img, shownAt}` — только показанные (черновики раздаток — на устройстве мастера). Пишет только мастер: на сервере поле лежит в `campaigns.data`, новых колонок и SQL нет. Старые поля книги с главами (`chapters`, `threads`, `pen`, `rotate`) не читаются и не удаляются. Нет поля — книга пуста.
- Заметки игроков (#203) идут через журнал: запись `log` с `kind: 'book'` и `text` — JSON правки `{op: 'note', note: {id, at, rev, edited?, blocks}} | {op: 'del', id}`; автор — `userId` записи журнала, а не поле внутри. Игрок правит и удаляет только свои заметки (правка с большим `rev` заменяет блоки), мастер удаляет любые. Клиент мастера, открыв кампанию (дом, книга или стол), переносит правки в `book.notes` (повтор ничего не меняет). Пока мастер не открыл кампанию, отряд читает заметку прямо из журнала; журнал грузится последними 120 записями — заметку, которую мастер не застал, после этого не видно. «Журнал бросков» записи книги не показывает.
- `Member = {userId, role: 'master'|'player', status: 'active'|'pending', characterId, joinedAt, lastSeen?, sceneId?}`. `sceneId` — личная сцена игрока, если отряд разделился.
- `invite = {code: 'RSP-XXXXXXXX', createdAt?, expiresAt|null, manual}`. Новые коды — 8 знаков (перебор по 4 был слишком дешёвым); старые 4-значные действуют, сервер принимает 4–8.
- `Character` — базовый шаблон листа (`makeCharacter` в `dist/js/data/demo.js`): `id, ownerId, name, portrait, classId/className, raceId/raceName, level, stats{str…cha}, saves[], skills[], ac, hp, hpMax, tempHp, speed, darkvision, deathSaves{s,f,stable?}, conditions[], attacks[], slots{}, spells, inventory, features, notes, initBonus, light, aura`. `personality` (необязательное, #202, `20261106150000`) — `{traits, ideals, bonds, flaws, appearance, backstory}`, только эти ключи, текст до 20000 символов или null; поле сборки: меняют владелец и мастер, видят все участники кампании. Детали листа — TASK-004. Спасброски от смерти (#197 R4, M1): три успеха — `stable: true` и счётчики с нуля, три провала (`f: 3`) — герой мёртв; мёртвый и стабильный не бросают; урон при 0 хитов — провал (крит — два) и снимает `stable`; урон сверх оставшихся хитов не меньше максимума — мгновенная смерть (`f: 3`).
- `Scene = {id, name, note, status, map{src, width, height}, grid{size, offsetX, offsetY, feet, visible, calibrated?}, lighting: 'bright'|'dark', fog{mode: 'vision'|'manual'|'off', ops[], explored[]}, walls[], lights[], terrain{difficult[], blocked[]}, tokens[], drawings[], pins[], portals[], traps[]}`.
- Мировые координаты — пиксели исходной картинки карты; клетка — `"c,r"` от смещения сетки.
- `Token = {id, kind: 'hero'|'foe'|'item'|'custom', characterId?, monsterId?, name, img, size, x, y, hidden, conditions[], hp?, hpMax?, tempHp?, ac?, speed?, initBonus?, light?, aura?, disengaged?}`. Хиты героя берутся из листа, существа и своего токена — с токена.
- Свои токены и призывы (TASK-097, необязательные поля; без них токен ведёт себя как раньше): `kind: 'custom'` — свой токен игрока (картинка; плашки и бой — когда задан `hpMax`; картинка `img` — `sb:@tokens/…`, `idb:…` или `ini:<имя>`); `ownerId` — владелец своего токена или призыва (нет — ведёт мастер); `summonedBy` — id токена призывателя; `mount: true` — ездовое; `riding` — id ездового, на котором сидит этот токен (всадник стоит в той же точке `x, y`); `layer` — ручной слой 0–2. Вид `kind` после создания не меняется.
- Своё существо игрока (#190 E, необязательное поле): `pending: true` у токена `kind: 'custom'` с `ownerId` — «ждёт мастера»: полупрозрачный, виден только владельцу и мастеру (другим игрокам клиент его не рисует; секрета в нём нет), в бой не попадает. Снимает `pending` мастер («Разрешить», с поправкой чисел); на сервере поле не входит в разрешённые игроку, игрок может только удалить своё существо («Отменить»). Числа карточки — обычные поля токена (`ac`, `hp`/`hpMax`, `speed`, `fly`, `initBonus`), незаданные не пишутся.
- Глаза существа (#190 C, необязательное поле; без него всё как раньше): `sight: [{to, ft}]` у токена существа (не героя и не предмета) — мастер дал герою `to` (id `Character`) глаза этого существа на `ft` футов (5–1000, кратно 5) от края существа. Игрок видит и своими глазами, и глазами существа: круг дальности, стены перекрывают, в темноте дальность действует как тёмное зрение. Глаза закрыты, пока существо скрыто, без хитов (`hp ≤ 0` при `hpMax > 0`) или без сознания. Пустой список не хранится; копия и вставка токена поле не наследуют. Пишет только мастер: на сервере поле не входит в разрешённые игроку (`guard_token`), новых колонок и SQL нет. «Отключить» у игрока — только у него на экране (событие `sight-off` мастеру), в данных не хранится.
- Рисунки сцены `drawings[]` (TASK-031 — объекты): `{id, type: 'line', color, pts[], author}` или `{id, type: 'text', x, y, text, color, size, author}`, или фигура (TASK-032) `{id, type: 'shape', shape: 'seg', a, b, color, author}` / `{id, type: 'shape', shape: 'cone'|'line'|'cube'|'sphere', origin, angle (рад), size (фт, дробный — по 0,5 фт; TASK-042), color, author}` — точка `origin` свободная, без привязки к клеткам; размер в футах переводится в пиксели по сетке сцены, как у шаблона линейки. Мастер выделяет, двигает, перекрашивает и удаляет любые, игрок — свои (`author`).
- Рисунки как в Owlbear Rodeo (TASK-182, необязательные поля; без них рисунок выглядит как раньше): фигура по рамке `{id, type: 'shape', shape: 'rect'|'ellipse'|'tri'|'hex', c{x, y} — центр, w, h — ширина и высота в px карты, rot — поворот в градусах 0–359, author}`; многоугольник `{id, type: 'shape', shape: 'poly', pts[], closed, author}` (`closed: false` — ломаная); кисть — `type: 'line'` с `closed: true` (контур от руки замкнут). Стиль у любого рисунка, кроме надписи: `width` — обводка в px карты (0 — без обводки, по умолчанию 4), `opacity` — непрозрачность обводки 0,1–1, `dash: true` — пунктир, `fill` — цвет заливки или `'none'` (только у замкнутых), `fillOpacity` — 0,1–1. Шаблон без поля `fill` заливается своим `color` на 18 %, как раньше. `z` — порядок наложения (больше — выше; нет — 0, при равных — порядок списка; на сервере порядок хранится в данных, а не в `ord`), `locked: true` — рисунок не двигают, не правят ручками и не стирают, пока его не открепят. Цвета в данных — только `#hex`, `hsl()/rgb()` или `var(--…)`, остальное заменяется цветом по умолчанию.
- Поворот и размер токена (TASK-030, необязательные): `rot` — поворот картинки в градусах 0–359; `scale` — свободный множитель диаметра к размеру по категории (0,25–8; средний × 1,4 = 7 фт), правила (клетки, досягаемость) по-прежнему считаются по `size`; `locked: true` — токен не сдвигает никто, пока мастер не снимет замок. `movedAt` < 0 — мастер отправил токен «под всех».
- `movedAt` (TASK-024, необязательное) — время последнего перемещения токена, мс; кого двигали позже, тот рисуется поверх. Нет поля — порядок по списку токенов сцены.
- Поля токена (TASK-023, необязательные): `disposition: 'hostile'|'neutral'|'friendly'|'secret'` (нет поля — враг для `foe`), `nameHidden` (игроки видят «Неизвестное существо»), `elevation` (фт над полом), `mapName` (#203, у токена героя: короткое имя на карте, в бою и бросках стола; лист не меняется; задаёт владелец героя или мастер — миграция `20261106130000`).
- Запись журнала броска: `vis: 'all'|'gm'|'blind'|'self'` (TASK-023); старое `hidden: true` без `vis` читается как `gm`.
- `aura = {name, radius (фт), color: 'magic'|'holy'|'fire'|'nature'|'frost'|'blood'|'shadow'|'#rrggbb', opacity?: 5–100 (%; нет поля = 16), text?, concentration?}`; у героя копия хранится и в листе. Ауры рисуются отдельным слоем под токенами (TASK-020).
- `Wall = {id, a{x,y}, b{x,y}, kind: 'wall'|'window'|'invisible'|'door'|'secret', open, locked, lockDc?, discovered?, name?}`.
- `combat = {active, sceneId, round, turn, entries[{tokenId, init|null, group?}], moved{tokenId: футы}}`; `init: null` — игрок бросит сам. `turn` — номер строки, с которой начинается слот хода.
  - Реакции (#197 M5): необязательное `combat.reacted: { [tokenId]: true }`. Только клиент мастера ставит отметку после броска атаки по возможности, удаляет в начале хода существа (у пачки — у всех её членов); начало и конец боя очищают карту. Отсутствие поля означает, что реакции доступны. Остальные способы расходовать реакцию пока отмечает мастер вне этой автоматизации; серверные правила не меняются.
  - Пачки в инициативе (#198, необязательное поле; без него бой идёт как раньше): `combat.entries[].group` — непрозрачный id пачки (`g-…`). Записи с одним `group` — один слот очереди: одна инициатива (у всех одинаковое `init`), один ход, «конец хода» один на пачку; в начале хода пачки `moved` обнуляется у всех её членов, расход движения — у каждого свой. Списка пачек и их имён в данных нет (бой читает каждый участник): имя и номер пачки клиент собирает из видимых ему токенов. `current` у пачки — первый живой видимый член, иначе первый живой. Пачку создаёт и меняет только мастер; игроку сервер по-прежнему даёт менять в записи лишь `init` с `null` (`guard_combat`), SQL не меняется. Группа призывов игрока (одинаковые призывы одного владельца и призывателя) — тоже `group`: с «Игроки бросают сами» её `init` = `null`, владелец бросает один к20 во все записи группы и сам заканчивает её ход (`ended` для своего призыва сервер уже разрешает).
  - Ничья по инициативе (#197 S1, необязательное поле): `combat.entries[].tie` — целое, порядок среди равных по `init`, задаёт мастер стрелками в очереди; идёт раньше бонуса и имени. Без поля ничья решается бонусом инициативы, как раньше. Сервер не меняется (бой пишет мастер).
- `log` — последние 120 записей `{id, at, userId, kind, label|text, total?, detail?, hidden?, vis?}`. Запись о хитах (`kind: 'hp'`) скрытого токена, токена с тайным именем и врага с неточными для игроков хитами пишется с `vis: 'gm'` — на сервере её текст уходит в `log_secrets`. «Журнал бросков» (меню кампании) показывает игроку только броски, которые ему положено знать; мастеру — всё.
- `settings = {diagonal: '5'|'5-10-5', sharedVision, playersSeeHp: 'status'|'exact', openMovement}`; `openMovement` (нет поля = `true`) — игроки двигают любые видимые токены (TASK-018).

Права в демо проверяются только интерфейсом (`canControlToken`, роль в членстве). Любая вкладка может записать что угодно в `localStorage`; скрытые токены, заметки мастера и ловушки физически лежат у игрока в браузере. Для игры по сети — серверный режим ниже (DEC-014); песочница остаётся как «Попробовать без входа».

## Реализовано: серверный режим (TASK-002, DEC-014)

Источник — `dist/js/server/**` (`config.js`, `client.js`, `model.js`, `sync.js`), миграции — `supabase/migrations/`, проверка прав — `supabase/tests/rls.sql`. Включается флагом `SERVER_ENABLED` в `config.js`; пока он `false` — ссылкой `?server=1` для своего браузера. Экраны и стол работают с той же формой `Campaign`, что выше: `model.js` собирает её из строк таблиц (`assemble`) и раскладывает обратно (`explode`, `diffRows`). Песочница (ключи выше) не меняется и на сервер не переносится.

### Таблицы (схема `public`, RLS на всех)

Ключи кампаний, героев, сцен, токенов и записей — строки, которые задаёт клиент (`c-…`, `ch-…`, `s-…`, `t-…`), как в песочнице. Пользователь — `uuid` Supabase Auth. Объекты сцены, токена, героя и т. п. лежат в `data jsonb` в той же форме, что в `rasputye-v2-db`, без полей, вынесенных в колонки.

**Токены игрока по матрице TASK-097** (миграция `20261030120000_own_tokens.sql`, TASK-123; охранник `guard_token`, понятный отказ на каждое запрещённое действие):

- Ставит: своего героя (`is_my_character` — по `characters.owner_id` или выбору в членстве); свой токен `kind: 'custom'` и призыв `kind: 'foe'` с `owner_id` = вошедший, призыв — со ссылкой `summonedBy` на свой токен или своего героя. Не скрытым, не закреплённым, не верхом, `data` до 64 КБ. Предметы и существа без призывателя ставит мастер.
- Меняет у своего героя: место, поворот, размер, свет, ауру, высоту, зрение, отход, езду. У своего токена и призыва — ещё имя, картинку, размер, союзность, ездовое, слой, статы, хиты и состояния. Вид, существо (`monsterId`), владелец, лист, скрытие и порядок — только мастер. Ссылку `summonedBy` можно только снять.
- Чужие видимые незакреплённые — только место и поворот, при открытом перемещении. Закреплённый (`locked`) не двигает и не поворачивает никто, кроме мастера, — владелец тоже.
- Для всех, включая мастера: токен стоит на сцене своей кампании (внешний ключ `(scene_id, campaign_id)` и понятный отказ «Сцена из другой кампании»); у экземпляра с листом один токен на кампанию (И1) — второй отклоняется «Этот герой уже на карте…», в том числе при двух одновременных запросах. Старые строки не проверяются и не удаляются.
- Езда: посадить (`riding`) может владелец всадника — на видимое ездовое той же сцены, без цепочек (посадки на сцене идут по очереди, поэтому две одновременные встречные посадки цепочку не создадут); спешить — владелец всадника, владелец ездового или тот, кто тянет всадника. Всадника, сидящего на ездовом, двигает любой, кто может двигать ездовое, если всадник встаёт в точку ездового.
- Удаляет: свой токен и призыв; героя и чужие — мастер. После удаления ездового всадники спешиваются, после удаления призывателя призывы остаются без ссылки.
- Бой и спасброски: инициатива (один раз), конец хода и результат спасброска — за любого героя и за свои токены. Добавить в бой — мастер.
- Несколько героев: `claim_character` даёт взять ещё одного свободного героя; первый выбранный остаётся `character_id` в членстве. Места по-прежнему считают игроков. Строка героя блокируется на время выбора: из двух одновременных запросов второй получает `taken`.

Функции записи токена (от имени вошедшего, RLS и охранник проверяют каждую строку):

| Функция | Что делает | Отказ |
| --- | --- | --- |
| `patch_token(id, set jsonb, unset text[])` | Меняет только переданные поля `data`, остальное — как на сервере | Токена нет или он скрыт — «Токен удалён мастером» |
| `adjust_token(id, {hp?, tempHp?})` | Прибавляет к хитам и временным хитам: хиты 0…`hpMax` (если `hpMax` — число, в том числе 0), временные ≥ 0. Одновременные вызовы учитываются оба | Герой — «Хиты героя меняются в листе»; другие поля — отказ |
| `move_tokens(scene, [{id, x, y, movedAt?, rot?}])` | Двигает до 50 токенов одной транзакцией, ездовые первыми; при отказе по любому не двигается никто | Другие поля, чужой токен, исчезнувший токен |

### Подтверждаемая запись листа TASK-004

Миграция `20261030140000_character_commands.sql` и отдельный клиент `dist/js/server/character-sheet.js` реализуют серверный путь листа. Путь подключён к окну листа и совместимым изменениям через sync; наличие файлов миграций не означает их применение на проекте Supabase. Дополнение `20261030140100_character_edits.sql` вводит команду `edit` для прежних элементов стола и уточняет проверку структурированных полей. Порядок выкладки — после human review и merge. Общий контракт экземпляров: полноценный герой, постоянный NPC и Sidekick используют `characters`; токен указывает на лист через `character_id`. Одноразовые существа и их `guard_token` остаются TASK-097.

Метаданные находятся в колонках, не в `characters.data`: версия (`bigint`, начиная с 0), признак использования нового пути и время архивирования. RPC возвращает версию **строкой**, чтобы не терять точность JavaScript. `data` сохраняет прежние плоские `hp`, `hpMax`, `tempHp`, `stats`, `slots` и неизвестные legacy-поля. Дополнительные необязательные поля: `profile: 'pc'|'creature'|'sidekick'`, `classes[]`, `resources[]`, `slotPools[]`, `hitDicePools[]`, источники/списки магии и структурированные разделы из плана TASK-004. Отсутствующий profile у старого героя означает `pc`; отсутствие числовых данных не означает 0.

| Данные ресурса | Форма |
|---|---|
| Старые ячейки | `slots[circle] = {max, used}`; circle — строка `1`…`9` |
| Новый ресурс/пул ячеек | `{id: string, max: integer, spent: integer, recovery?, ...}` в `resources[]`/`slotPools[]` |
| Пул костей хитов | `{id: string, die, total: integer, spent: integer, ...}` в `hitDicePools[]` |
| Состояния | строки или записи с `id`; их текст не исполняется автоматически |

**Создание героя (TASK-186 P4a, `20261105100000_character_create.sql`).** `create_character_sheet(campaign, characterId, operationId, data, claim)` — одна транзакция: проверка формы, запись листа (`sheet_managed`, версия 0, владелец — `auth.uid()`), запись `create` в истории и, если `claim`, выбор героя игроком. Оба ID — UUID от клиента, хранятся с черновиком до ответа: повтор той же операции с тем же запросом возвращает прежний ответ (`replayed: true`), другой запрос с тем же ID операции — `22023`, занятый ID героя — `23505` (новая попытка — новый ID). Создаётся только `profile: 'pc'`; служебные поля (`ownerId`, версия, архив) задаёт сервер. `data.creation` — неизменяемый блок происхождения версии 1 (`schemaVersion`, `edition: '5e-2014'`, `rulesRevision`, `levelHistory[1..20]` с классами SRD 5.1, `selections`, `ancestry`, `background`, `abilityInput`, `verified: 'client'`); выборы внутри него сервер пока не перепроверяет — это P4b. Уровень и классы должны совпасть с историей уровней, `hpMax` — с формулой `character_creation_hp` (клиент — `creationHitPoints` в `sheet-rules.js`). Клиент: `makeCreateRequest` / `create` в `server/character-sheet.js`; данные листа собирает `toCharacterData` (`rules/character-builder.js`).

**Проверка сборки (P4b, `20261106170000`).** Edge Function `validate-build` (`supabase/functions`, правила — `rules/build-check.js`, те же файлы, что у браузера) пересчитывает сборку из `data.creation` и сверяет числа, классы, навыки, заклинания и ячейки; честную сборку отправляет в `create_character_sheet` или `level_up_character` от имени игрока с заголовком `x-build-check`. Пометку `creation.verified` ставит только триггер `characters_verified`: `'server'` при верном ключе (в базе — его SHA-256, `build_check_key`), иначе `'client'`; правка без смены сборки её не меняет. Подделать пометку из браузера нельзя. Функция не отвечает или сборка не сошлась — герой всё равно создаётся, с пометкой `'client'`; запретить такие сборки пока нельзя (политики кампании нет в интерфейсе).

**Повышение уровня (#202, `20261105110000_character_level_up.sql`).** План — `levelUpPlan(character, classId, catalogues, { policy })` в `rules/level-up.js` (решения нового уровня, способности, прибавка хитов); тело команды — `levelUpPayload` после выборов; запись — `level_up_character(campaign, characterId, expectedVersion, operationId, { creation, patch })`, клиент — `makeLevelUpRequest` / `levelUp`. Только герой, созданный конструктором (`profile: 'pc'`, `creation` версии 1); меняют владелец или мастер. `creation.levelHistory` растёт ровно на один, прежние уровни, раса, предыстория, ввод характеристик и ревизия правил не меняются; `patch` — только поля сборки (`level, classes, classId, className, stats, proficiencies, speed, darkvision, hitDicePools, slotPools, resources, spellSources, knownSpells, featureEntries`). `hpMax` и `hp` прибавляет сервер — разницей `character_creation_hp` до и после, поэтому прежние ручные правки максимума сохраняются. Записи списков сохраняют прежние ID и потраченное (кость — по кости, ячейки — по виду и кругу, остальное — по `ref`/имени). Протокол — как у `character_command`: ожидаемая версия, повтор по `operationId`, история `level_up`.

«Мои герои» (DEC-019 D1): таблица `heroes` (`id`, `owner_id`, `data`, `archived_at`), только владелец, не больше 100 героев, размер `data` до 512 КБ. Браузер держит копию, при входе сводится с базой по `data.updatedAt`.

Бой (D4): `combats` читает только мастер; игроки читают `combat_public` — копию, которую ведёт база: без скрытых токенов мастера, `current: "?"`, если ходит скрытый, `turn: 0`.

Броски характеристик (D3): `creation.rollReceipts[{dice, source, sig}]`; кубы бросает и подписывает функция `validate-build`, неподписанные броски оставляют сборку непроверенной.

Производные героя из конструктора: `ac` и `initBonus` не хранятся, КД и инициативу считает `rules/hero-derived.js` (лист и стол одинаково); запись на листе важнее. В `knownSpells` у заклинаний домена и клятвы стоит `alwaysPrepared: true`: они не входят в предел подготовленных.

**Простое повышение старого героя (`20261105120000_character_level_up_simple.sql`).** Герой без `creation` (прежние `classId`/`level` или `classes[]` с `ref`): `levelUpPlan` отдаёт `mode: 'simple'` — без выборов, с заметкой, что черты, заклинания и прибавки характеристик игрок вносит на листе вручную. `patch` — только `level`, `classes`, `hitDicePools`: ровно +1 уровень одному классу SRD или новый класс с 1 уровнем в конце списка (мультикласс — по политике кампании). Хиты сервер прибавляет сам: среднее кости класса + модификатор Телосложения. После команды лист становится управляемым (`sheet_managed`).

Для каждого счётчика `0 ≤ spent/used ≤ max/total`; ID в списке уникальны. Ресурс без известного расхода/максимума нельзя автоматически менять. Новый ресурс настраивает владелец или мастер через проверяемый patch; управляющий меняет существующий расход. Верхняя техническая граница целых — `Number.MAX_SAFE_INTEGER`, размер data/запроса до 256 КиБ. Проверка типов и диапазонов не доказывает законность всех D&D-сборок.

`read_character_sheet(p_campaign, p_character)` возвращает `{id, campaignId, ownerId, version, managed, archivedAt, data, controllers[]}`. Полный лист, включая архивный, читают активные участники кампании. Чтение не активирует новый путь и не мигрирует данные. Посторонний/ожидающий/исключённый участник не получает лист через RPC. Этот доступ не раскрывает библиотеку мастера или статблоки одноразовых врагов.

`character_command(p_campaign, p_character, p_expected_version, p_operation, p_kind, p_payload)` — одна атомарная операция. `p_operation` — UUID, `p_expected_version` — полученная версия. Ответ: `{ok:true, operationId, replayed, sheet}`. Разрешения проверяются заново **перед** возвратом повтора. Ключ повтора привязан к кампании, пользователю, листу и полному содержимому запроса; другой payload с прежним ID отклоняется. Одновременный повтор сериализуется; исходный ACK хранится без TTL и не применяется второй раз. Периодическая очистка таблицы повторов в эту версию не входит.

| Команда | Payload | Кто вызывает |
|---|---|---|
| `patch` | объект разрешённых изменяемых полей; объекты объединяются рекурсивно, списки заменяются явно; неизвестные исходные поля остаются | владелец/мастер; смена profile и уровня Sidekick — мастер |
| `set_current` | `hp?`, `tempHp?`, `conditions?`, `deathSaves?`, `concentration?` | владелец, мастер, управляющий |
| `adjust` | `hp?: delta`, `tempHp?: delta`, `counters?: [{field,id,delta}]` | владелец, мастер, управляющий |
| `rest` | `{kind:'short'|'long', conditionsConfirmed:true, adjust:{...}}` | владелец, мастер, управляющий; условия игры подтверждает человек |
| `growth` | `{patch:{...}}` для Sidekick | мастер |
| `controller` | `{userId:uuid, enabled:boolean}` | владелец/мастер; назначаемый должен быть активным участником |
| `archive` / `restore` | `{}` | владелец своего, мастер любого листа |

`counters[].field` ограничен `slots`, `resources`, `slotPools`, `hitDicePools`; `id` — круг старой ячейки или стабильный ID записи. Положительная delta увеличивает потраченные единицы, отрицательная возвращает. `hp < 0` наносит урон: временные HP поглощают первыми; положительная delta лечит не выше максимума. `set_current.tempHp` заменяет значение, а не выдаёт автоматическое сложение новых временных HP. При 0 HP PC/Sidekick отмечается бессознательное состояние; лечение с 0 снимает его и сбрасывает счётчики смерти. Иные состояния не сбрасываются; бросок, сопротивления, эффекты текста и законность отдыха не исполняются этим RPC.

Сервер блокирует строку листа и сверяет версию; несовпадение — SQLSTATE `40001` с актуальной версией в details, без записи. Ошибка любой части команды откатывает ресурсы, историю, ключ повтора и архив/бой целиком. `42501` — отказ прав, `P0002` — не найдено, `P0001` — архив, `22023` — неверный ввод. Отрицательное/превышающее остаток изменение ресурса отклоняется, не обрезается молча. Новая версия, история и ответ повтора фиксируются одной транзакцией.

**Контракт ошибок команд листа (TASK-004 2.2).** Все команды листа (`character_command`, `create_character_sheet`, `level_up_character`) отвечают одним набором SQLSTATE; клиент `server/character-sheet.js` переводит их в `SheetCommandError.kind`:

| SQLSTATE / причина | `kind` | Что делать клиенту |
|---|---|---|
| `40001` — версия листа устарела или место героя занято | `conflict` | перечитать лист, показать расхождение, пересобрать правку; повтор того же запроса не поможет |
| `42501` — нет права (не владелец/мастер, управляющий меняет сборку, лист недоступен) | `forbidden` | не повторять |
| `22023`, `22P02`, `22003`, `23503` — неверные данные: тип, целое вне диапазона, дробный счётчик, расход сверх максимума, пустая строка вместо числа, повтор ID записи, запрещённое поле (`ownerId`, служебные) | `validation` | показать сообщение сервера; черновик не теряется |
| `23505` — ID героя уже занят | `duplicate` | новая попытка с новым ID |
| `P0002` — лист не найден | `not_found` | закрыть лист |
| `P0001` — лист в архиве | `archived` | восстановить через мастера |
| нет ответа / обрыв сети | `network` (`retryable`) | `retry(error)` — тот же замороженный запрос с тем же `operationId` |
| ответ не той формы | `protocol` (`retryable`) | как `network` |

Любой отказ откатывает команду целиком: частичной записи нет (проверяется в `supabase/tests/rls.sql` и `local_pg.py`).

Архивирование снимает все токены листа в кампании и их записи боя, очищает их бюджет движения; текущий ход передаётся следующему без возврата уже завершённого хода. При переходе через конец очереди раунд увеличивается один раз, пустой бой завершается. Лист и история остаются. Восстановление возвращает **тот же** лист с прежними ресурсами без автоматического возврата токена/старого хода. Постановка токена проверяет, что лист существует в этой кампании и не в архиве; гонка постановки с архивом сериализуется. Очистка связей ездового/призыва при удалении токенов согласуется с реализацией TASK-097.

Назначение управления не передаёт владение или сборку. Прямая запись в `character_controllers` ролям API запрещена; RLS разрешает участникам читать список. Выход/исключение или перевод управляющего в pending удаляет назначение; повторное вступление не возвращает его автоматически. `can_control_character(campaign, character)` доступен для интеграции guard_token в TASK-097 и проверяет активное членство, неархивность, владельца/мастера/назначение. На карте эти права до TASK-097 не включаются самим наличием таблицы.

#### Совместимость и включение

Старые строки остаются `sheet_managed=false`; прежние записи сохраняют прежний путь, но повышают версию и оставляют историю будущих изменений. **Первый успешный character_command** переводит конкретный лист в `sheet_managed=true`. После этого прямой UPDATE/DELETE листа ролями API запрещён, в том числе мастеру: данные пишутся через команды с версией. ID кампании/листа и служебные метаданные не принимаются в patch. Старый свободный текст и неизвестные поля не удаляются; прошлую историю до этой миграции сервер не выдумывает.

Sync переводит обновления Character с серверной `sheet_version` на `edit`: сравнивает dirty-поля с последней подтверждённой строкой, отправляет отдельные delta расхода и не затирает неизменённое. До установки миграции (метаданных нет) сохраняется прежний путь. Передача владельца и связанного выбора героя в Member объединяется одной командой; её поля доступны только мастеру. Управляемый лист не обновляется прямым UPDATE, в том числе из token bar или undo. Кэш подтверждённых версий отделён от оптимистических изменений; событие Realtime не заменяет ожидающий локальный ввод. Он создаёт неизменяемый запрос, ждёт ACK, возвращает типизированную ошибку и сохраняет запрос для явного повтора с тем же UUID. После повторного ACK перечитывает актуальный лист, чтобы не подменить его историческим снимком. При конфликте UI сохраняет черновик и предлагает сверку; новый расчёт получает новую команду/UUID.

При откате UI таблицы/поля и данные сохраняются; управляемые листы не переводятся молча обратно в legacy. До совместимой версии UI запись в них должна оставаться отключённой с явным сообщением. Обратное переключение протокола/удаление колонок — отдельная согласованная миграция после проверки данных. Применение на проекте Supabase в рамках подготовки PR не выполняется.

Проверки: `node --test tests/character-sheet-client.test.js tests/sheet.test.js`; `python3 supabase/tests/local_pg.py` создаёт изолированный PostgreSQL в `/tmp` с приватным Unix-сокетом, применяет миграции, запускает `rls.sql` и гонки двух сессий, затем удаляет кластер. Нужны локальные `initdb`, `pg_ctl`, `psql`. Auth/Storage/Realtime в этом тесте — минимальные схемы, а не проверка JWT/PostgREST/реального проекта. Песочница автоматически на сервер не переносится.

#### Формат редактора и черновика TASK-004

Лист открывается по ID Character, без зависимости от токена. `readCharacter` читает структурированные записи поверх legacy-представления; исходный объект и старые строки `spells`, `inventory`, `features`, `hitDice` остаются без автоматической конвертации. Сами вкладки используют глубокий черновик исходного JSON, отправляя только изменённые поля.

| Раздел | Записываемые необязательные поля | Поведение |
| --- | --- | --- |
| Личность | `classes[{id,name,subclass,levels}]` плюс прежние имя/происхождение/предыстория | Общий `level` синхронизируется с суммой уровней классов. Пустой список сохраняет legacy level |
| Владения | `proficiencies.saves/skills` — карта множителей `0/0.5/1/2`; `languages`, `tools` — свободный текст | Модификатор + округлённый вниз PB × множитель; неизвестное основание даёт неизвестный итог |
| Исключения | `overrides.saves/skills[id]` и `overrides.proficiency`: `{value,reason}` | Числовой итог заменяет расчёт один раз; нулевой итог действителен, пустой отключает override; причина хранится отдельно |
| Бой | Прежние HP/КД/ходьба/инициатива/состояния; `movement.fly/swim/climb/burrow` | КД и движение ручные. Пустой `initBonus` использует DEX для броска в листе. Автоматических эффектов снаряжения нет |
| Кости | `hitDicePools[{id,name,die,total,spent}]` | Неизвестный расход требует уточнения; legacy-строка не означает все кости доступными |
| Атаки | `attacks[{id?,name,ability,proficient,bonus,damage,type,note}]` | `bonus` — явный ручной итог (включая старый); при null расчёт по выбранной характеристике и владению. Урон бросается отдельно и сам никому HP не меняет |
| Действия | `actions`, `bonusActions`, `reactions`: записи `{id,name,description,formula?}` | Текст не исполняется. Полная типизированная механика save target/self, recharge и легендарных/логовных действий остаётся дальнейшей частью статблока |
| Магия | `spellSources[{id,name,ability,kind,attackOverride,dcOverride}]`; `knownSpells[{id,name,circle,sourceId,prepared,ritual,description}]` | Атака = характеристика + PB, Сл = 8 + характеристика + PB; отдельные ручные значения. Источник выбирается явно. Подготовка/ритуал не исполняют заклинание |
| Снаряжение | `inventoryItems[{id,name,quantity,weight,equipped,attuned,description}]`, `coins.{cp,sp,ep,gp,pp}` | Собственные названия сохраняются; удаление настроенного предмета требует подтверждения; лимиты и классовые исключения ручные |
| Особенности | `featureEntries[{id,name,source,description}]`, `resources[]` | Текст не выдаёт работающий эффект, ресурс имеет явное правило восстановления |
| Заметки | Прежний `notes` | Видны всем активным участникам, приватных разделов нет |

`edit` принимает `{patch?,current?,adjust?,ownerId?,membership?}`. `current` разрешает только текущие HP/temp/состояния/смерть/концентрацию; `patch` сборки — владельцу/мастеру. `adjust.currentHp` — уже рассчитанная разница текущих HP (старый UI уже поглотил урон временными); она не совмещается с семантическим `adjust.hp`. Смена owner и Member.character_id проверяется и применяется целиком, только для старого/нового владельца и текущего листа. Ошибка откатывает обе стороны передачи.

Сохранение в окне явное. Во время запроса поля заблокированы; подпись «Сохранено» появляется после ACK. Сбой сохраняет черновик и неизменяемый запрос для повтора. Ключ `sessionStorage`: `rasputye:sheet-draft:<server|sandbox>:<userId>:<campaignId>:<characterId>`, значение `{base,draft,invalid,pending}`. Он не переносится между пользователями и режимами; черновик существует в текущей вкладке (не резервная копия между браузерами). При закрытии доступны сохранить/оставить черновик/продолжить ввод. Ошибки прежних элементов стола тоже сохраняют ввод под этим ключом, даже если окно закрыто.

При сверке серверного снимка независимые dirty-поля накладываются на новую базу; конфликтующие поля показывают оба значения и требуют выбора. Массивы сверяются целиком: добавленные записи не сливаются по догадке. Повтор потерянного ACK использует тот же UUID и исходный payload даже после закрытия окна. Старая версия кэша не запускает повторную загрузку уже прочитанной новой версии. При отзыве прав сервер отклоняет запись, черновик доступен для разбора.

Отдых предлагает ручной путь и предпросмотр. Короткий принимает отдельные введённые результаты выбранных костей с CON; продолжительный восстанавливает HP и не больше половины общего числа костей (минимум одну), при нескольких типах просит распределить возврат. Восстанавливаются только явно заданные short/long/both ресурсы; manual и неизвестное остаются для ручного учёта. Temp HP без явного основания истечения и состояния не сбрасываются. Применение — одна `rest` с подтверждёнными условиями, ожидаемой версией и UUID. Полную законность отдыха определяют участники, классовые тексты не исполняются.

Песочница остаётся локальной: права — интерфейсные. Она сохраняет тот же черновик, сверяет три версии перед записью и архивирует лист с токенами/боем одним local commit. Серверный архив — настоящая транзакция; SQL сортирует участников по инициативе и бонусу перед передачей хода. Для равных инициативы и бонуса используется ICU collation `ru` (как localeCompare в UI), при равных именах сохраняется порядок записей. PostgreSQL должен поддерживать ICU; это проверяет применение миграции на тестовой БД.

Браузерные проверки: `tests/browser/sheet/e2e.mjs` (песочница, черновик, неизвестный HP, экспертиза, отдых, архив/восстановление, просмотр, 390 px), `tests/browser/sheet/server.mjs` (fake Supabase: ACK, потеря ответа, повтор UUID, legacy bridge, конфликт). Они требуют Playwright/Chromium и локальный HTTP сервер; никаких секретов или реального Supabase. SQL: `supabase/tests/local_pg.py` применяет обе миграции на изолированном настоящем PostgreSQL. Сценарий старого общего browser/server-e2e доходит до загрузки карты, но использует отсутствующий в текущей панели `add:map`; этот незатронутый сценарий не объявляется зелёным.

Реальное время: изменения этих таблиц (Realtime проверяет RLS для каждого получателя; удаления приходят всем подписчикам таблицы только с ключом — клиент сам отсекает чужие кампании), Broadcast `bus` и Presence на приватном канале `campaign:<id>` (только участники), личный канал `user:<uid>`. Мастер, скрыв токен, рассылает `hidden-ids`, чтобы игроки убрали его у себя. Скрытый бросок в Broadcast идёт без суммы.

Карты и обложки: приватный бакет `maps`, путь `<campaign_id>/<uuid>.<ext>`, в данных ссылка `sb:<путь>`; браузер получает подписанную ссылку на 6 часов. Читают участники и ожидающие, загружает мастер, до 25 МБ, только картинки.

Картинки своих токенов (TASK-123): приватный бакет `tokens`, путь `<campaign_id>/<user_id>/<файл>`, PNG, JPEG или WebP до 5 МБ. Читают участники кампании, загружает и меняет владелец папки, удаляют он и мастер. В данных токена ссылка `sb:@tokens/<путь>` (TASK-183, `uploadTokenImage` в `dist/js/server/sync.js`); в песочнице картинка своего токена — `idb:` в этом браузере, как карта. Файл после удаления токена в бакете остаётся.

## Личная библиотека Creature (TASK-122, TASK-125)

Эта порция предоставляет модель и API; экран библиотеки, постановка на сцену и копирование изображений в кампанию — TASK-097 у Claude. Невлитый PR не означает наличие функции на сайте. Общая поставка содержит SRD и каталог метаданных; личные не-SRD статблоки не публикуются в Git или общем каталоге.

`Creature = {id, ownerId, name, img, statblockImage?, size, type, alignment, ac, acNote, hp, hpFormula, speed{walk,fly,swim,climb,burrow}, stats{str,dex,con,int,wis,cha}, saves[{ability,bonus}], skills[{name,bonus}], senses, languages, cr, traits[], actions[], bonusActions[], reactions[], legendary{count,actions[]}, source:'manual'|'image', updatedAt}`.

Возможность: `{name,text,attack?{bonus,reach,range{normal,long}},damage?[{dice,type}],save?{ability,dc,who:'target'|'self'},recharge?}`. Расстояния в футах. Неизвестные числа — `null`, включая неполный статблок картинкой; такая запись не становится автоматически пригодной к бою. Обязательны ID/владелец/имя; image требует statblockImage. `cr` — строка (`'1/4'`, `'2'`) либо null. Копия SRD сохраняет provenance (исходный ID, атрибуция CC BY 4.0), исходную прозу и дополнительные JSON-поля. Сырой saving_throw без известного субъекта не превращается в типизированный save. Несколько компонентов урона сохраняются отдельно.

| Хранилище | Форма и границы | Кто читает/пишет |
| --- | --- | --- |
| Песочница, `rasputye-v2-db` | Необязательное `creatures:{[JSON.stringify([ownerId,id])]:Creature}` на верхнем уровне, версия 1 и campaigns сохраняются; до 500 на ownerId. | `public.creature_library_quota` | Внутренний `owner_id,used` (0–500), AFTER INSERT/DELETE; upsert-update не расходует место | API доступа не имеет; атомарный счётчик выдерживает параллельные вставки |

Постановка своего существа: портрет и изображение статблока сначала копируются из личного `library` в бакет `tokens` кампании. Каждая постановка создаёт новый снимок текущего шаблона (группа токенов одной постановки делит снимок); правки библиотеки не меняют прежние снимки. В серверном режиме токен и успешное уведомление показываются после подтверждения записи. Снимок и первый токен отправляются `place_creature`, остальные токены — обычными вставками; при отсутствии RPC используется прежний путь вставок. Формат строк и права не изменены; новой локальной очереди сохранений нет.

На клиенте максимум — 65536 байт нормализованного JSON в UTF-8. База отдельно ограничивает `data::text` (JSONB) тем же пределом; его пробелы и порядок сериализации могут отклонить пограничную запись раньше. Ошибка возвращается, данные не обрезаются. Размер/MIME ограничены bucket и клиентом; клиент проверяет сигнатуру, а не только расширение. Подписанные URL выдаются на 60 секунд и не сохраняются в статблоке; это временная ссылка, не мгновенно отзываемая сессия. `resolveLibraryImage` не является общим resolver картинок стола; подключение делает UI TASK-097.

Квота файлов утверждена Ярой при исправлении review PR #150: **100 МиБ и 200 файлов на владельца**, до 5 МиБ каждый. Триггеры `storage.objects` затрагивают только bucket `library`: BEFORE проверяет путь/ссылки и блокирует строку счётчика владельца; AFTER учитывает INSERT/DELETE и разницу размера UPDATE, включая upsert без двойного подсчёта. Размер — `metadata.size`. В откатываемой проверке разрешения Storage размер ещё может отсутствовать и считается нулём; `contentLength` игнорируется, поскольку включает multipart overhead. Окончательная запись Storage API содержит фактический размер. Отказ откатывает и объект, и счётчик. Квота ограничивает сохранённые объекты, а не параллельный входящий сетевой трафик.

Сохранение Creature с `img/statblockImage=library:…` проверяет владельца и наличие файла под той же блокировкой. Удаление Storage отвергается, пока хотя бы одна личная запись ссылается на файл. Гонка удаления с сохранением заканчивается успешной операцией одной стороны и явной ошибкой другой; битая ссылка не сохраняется. Перемещение/переименование файла запрещено; в кампанию создаётся отдельная копия.

`getLibraryImageUsage()` → `{files,bytes,maxFiles:200,maxBytes:104857600}`, `listUnusedLibraryImages()` → `[{ref,bytes}]`, `cleanupUnusedLibraryImages()` → `{removed:[ref],failed:[{ref,message}]}`. Только явная очистка серверной библиотеки: вызывает `library_unused_images()` (личный список), затем Storage API `remove` и требует подтверждения каждого удаления. Повторная проверка ссылок происходит в базе при DELETE. Связанные файлы и чужие объекты не очищаются. Песочница сообщает, что серверная квота/очистка недоступны; общий IndexedDB карт этим API не удаляется. Фоновая задача/удаление по возрасту не вводятся; UI с подтверждением очистки подключает Claude.

Supabase [рекомендует считать storage schema доступной только для чтения](https://supabase.com/docs/guides/storage/schema/design). Добавленные guard/count triggers — явное расширение для серверной квоты и защиты ссылок; они записывают только наш счётчик, не изменяя Storage metadata самостоятельно. [Удаление реальных объектов выполняется только через Storage API](https://supabase.com/docs/guides/storage/management/delete-objects). Совместимость с реальной версией Storage API должна быть проверена перед включением uploads; локальный SQL-стенд не заменяет эту проверку.

`dist/js/core/library.js`: `listCreatures()`, `saveCreature(value)`, `deleteCreature(id)`, `copySrdCreature(monster)`, `uploadLibraryImage(file)`, `resolveLibraryImage(ref)` — Promise. Новые ID создаёт клиент, ownerId берётся из текущего входа. Сохранение возвращает подтверждённую сервером строку либо ошибку; sandbox не скрывает ошибку localStorage. Серверная библиотека не входит в store, sync/model или Realtime кампании. Ответ от предыдущего пользователя/режима отклоняется; кэша личных записей между аккаунтами нет.

Все личные обращения используют пару ownerId/id; один `source_id` снимка кампании остаётся только происхождением и не разрешает искать личную запись без её владельца. Серверный upsert использует конфликт `(owner_id,id)`. Песочница считает уникальные ID владельца, при совпадении старого и составного ключей выбирает составной; чужая старая запись с тем же ID не удаляется.

`createLibrary` и `createServerLibrary` позволяют внедрять адаптеры для тестов. Проверка SQL: `python3 tests/postgres/library_harness.py` (локальные PostgreSQL binaries). Стенд создаёт отдельный временный кластер без TCP, применяет миграции и проверяет реальные RLS/триггеры/гонку; auth/storage/realtime моделируются минимальными схемами. Это не проверка работающего Supabase HTTP Storage API. На рабочий проект эти миграции до review/merge не применялись.

### Объект кампании

- `name: string` — название; `round: number` начинается с 1; `turn: number` — индекс текущего участника отсортированного списка.
- `tokens: Token[]`; `notes: string`; `logs: LogEntry[]` (код оставляет последние 60 записей).
- `grid: boolean`, `fog: boolean`, `paths: Point[][]`.
- `map?: string` — JPEG data URL после обработки загруженной картинки; исходная SVG-карта встроена в HTML.

`Token = {id, name, kind, hp, max, ac, mod, x, y, init}`. `kind` — `hero | enemy`; `init` — `number | null`; `x/y` — проценты размеров карты. Стартовые ID `a…e`, новые — UUID. Имена и порядковые номера не являются ID. Токен сейчас совмещает представление на сцене и боевые данные героя; полноценного листа отдельно нет.

`Point = {x, y}`. `LogEntry = {label, result, detail, time}`; `result` может быть числом или строкой, `time` — локальная строка `HH:MM`, не полноценная временная метка.

В демо мастер меняет всю кампанию. Игрок меняет HP и положение выбранного `hero`; интерфейс скрывает инструменты мастера. Все данные, включая `notes`, по-прежнему лежат на одном устройстве. Скрытие UI не обеспечивает конфиденциальность. Экспорт — JSON кампании без темы/сессии; импорта пока нет.

### Порция NPC и Sidekick TASK-004 (ещё на review)

В окне доступны создание общего PC/NPC/Sidekick и независимая копия. Для SRD используется существующий runtime-каталог и адаптер TASK-122; сохраняются базовый снимок, provenance и SHA-256 содержимого шаблона. Обновление каталога не меняет экземпляр. Изображение загружается через существующий asset-путь; серверная загрузка остаётся доступна мастеру. OCR и автоматического применения эффектов нет. Дополнение `20261030140200_character_statblocks.sql` проверяет типы, размер UTF-8, явный save actor, override и параметры Sidekick.

`sidekick` хранит class warrior/expert/spellcaster, baseLevel/baseSnapshot, hitDie, выбранные partyIds и локальные записи growthHistory. Авторитетная история операций — character_history. Подсказка среднего не меняет уровень. Мастер подтверждает предпросмотр роста или явную ручную корректировку; текущие HP и базовый снимок сохраняются. Прирост костей отделён от неизвестных базовых костей. Классовые выборы и итоговые бонусы исходного статблока остаются ручными; формулы по уровню используют новый PB. Полные таблицы классов и произвольные зависимости не автоматизированы.

Проверки: два новых browser-сценария (песочница и fake Supabase), 199 реальных локальных SQL-проверок и четыре гонки. На production ничего не применено. Остаются полный проход примеров, интеграция карты/связей и прав движения с TASK-097, доведение всей матрицы UI и финальный человеческий review. Галочки незавершённых задач не означают готовность этих частей.

#### Прирост Sidekick и повтор команды

Каждое подтверждение роста создаёт новый `hitDicePools` элемент `{id,name,source:'sidekick-growth',operationId,die,total,spent:0}`. Приросты не объединяются с базовыми костями или предыдущими операциями. `sidekick.growthHistory` получает `{id:operationId,operationId,kind,from,to,hpFrom,hpTo,note}`; UUID совпадает с character_command.operationId. Канонический серверный audit остаётся character_history. Переключение уровня или повтор потерянного ACK не создаёт второй прирост. У ранее записанных пулов без operationId сохраняется прежний формат; их ID и расход не переписываются.

Неприменённый предпросмотр не меняет сущность. После изменения введённых результатов требуется повторный расчёт; после внешнего изменения исходных значений старый результат отклоняется, результаты костей остаются в окне. Подсказка группы изменяет только выбранные partyIds после явного сохранения, а не уровень. Проверки: tests/browser/sheet/growth.mjs, дополнительный growth-сценарий в server.mjs, unit sheet.test.js и RLS-сценарий повтора growth (204 проверки суммарно до интеграции с #126). Production SQL не запускается.

Character-миграции имеют порядок 20261030140000/140100/140200 после own_tokens120000 и creature_library130000. Это ещё не применённые файлы; наличие в Git не разрешает применение в production. Перед установкой оператор сверяет live-историю и свободность версий.

### Токены: постановка существа и хиты прибавкой (TASK-097, `20261105130000_token_097_rest.sql`)

- `place_creature(creature, token)` — снимок `campaign_creatures` (если его ещё нет) и токен, ссылающийся на него (`data.monsterId = 'lib:<id>'`), одной транзакцией; права — RLS обеих таблиц (функция `security invoker`). Клиент сам собирает пару вставок в одну операцию (`groupPlacements`); без функции на сервере — две вставки, как раньше.
- `adjust_token_once(id, {hp?, tempHp?}, operationId)` — прибавка хитов токена не-героя с ключом повтора: тот же ID и запрос → прежний ответ (`replayed: true`), другой запрос → `22023`, удалённый токен → `P0002` «Токен удалён мастером». Клиент шлёт разницу, если изменились только числовые `hp`/`tempHp`; иначе — `patch_token`.
- `campaign_creatures` — в публикации Realtime; клиент подписывается, только если таблица есть на сервере, удаления фильтрует по `campaign_id` из ключа.
- Картинка удалённого токена (`sb:@tokens/<кампания>/<пользователь>/<файл>`) удаляется из бакета, если на неё больше не ссылаются токены, снимки и листы кампании (мастер или хозяин папки).

### Заявки токенов игрока (#203)

Любой новый токен игрока (герой, свой токен, призыв из каталога/библиотеки, файл картинки) сохраняется с `Token.pending: true`. BEFORE-триггер `tokens_approval` принудительно выставляет JSON boolean true даже старому или изменённому клиенту. Ожидающий токен — заявка: виден мастеру и автору, не двигается, не участвует в бою, не даёт свет/зрение. Игрок может отменить заявку удалением; менять ожидающий токен нельзя. Мастер разрешает снятием `pending` или отклоняет удалением. Уже существующие токены автоматически не переводятся в ожидание. Постоянная очередь мастера объединяет сцены.

Встречи (#203): `monsters[].id` принимает id бестиария или `libsrc:<Creature.id>`. Для личного существа `creature` — сохранённая копия шаблона на момент добавления; актуальная библиотека имеет приоритет, а при удалении шаблона остаётся копия. Ссылки на личные картинки приватны и при постановке переносятся в кампанию тем же путём, что вкладка «Мои». Короткое создание сохраняет шаблон в личную библиотеку и сразу добавляет его во встречу. Вкладка «Встречи» за столом доступна мастеру; перетаскивание ставит состав на текущую сцену у точки отпускания, ссылка из дома учитывает привязанную сцену. Встречи остаются локальными для кампании и пользователя. API `commitCreatures` / `persistCreatureTokens` дополнительно принимают массив снимков (прежний одиночный снимок поддержан); это одна запись истории на весь состав.

При отмене постановки встречи её снимки остаются в кампании для истории и повторного использования изображений. В серверном режиме повтор такой записи истории выполняется через подтверждённую постановку после загрузки кампании, а кнопки отмены/повтора ждут ACK; обычные записи истории сохраняют прежнее синхронное поведение. При недоступном исходном файле личного портрета постановка выдаёт ошибку: сохранённая копия Creature не резервирует файл, удалённый из Storage.
