# Постоянные ветки направлений

Ветка соответствует фронту работы и переиспользуется для последовательных задач. Каждая задача сохраняет собственные TASK-ID, Issue и OpenSpec change. Префиксы codex/claude не назначают человека или инструмент владельцем направления.

| Направление | Ветка | Граница |
| --- | --- | --- |
| Сетевой аудит и диагностика | `codex/network` | Текущая TASK-035 — аудит. Runtime/SQL TASK-002 остаются у их исполнителя до явного разделения/передачи. |
| Правила и каталоги D&D | `codex/rules5e` | Данные и механики; подключение общих UI/контрактов согласовать. |
| Голос и аудио | `codex/voice` | Аудиофункции; общие данные/интеграции согласовать. |
| Основной интерфейс и текущий серверный этап | `claude/dev` | Существующий фронт разработки; не имеет особых прав на merge. При разделении UI/backend команда заранее фиксирует новые границы. |
| Координация процесса и документация | `codex/process` | Правила, шаблоны, OpenSpec-процесс; продуктовый код не входит автоматически. |

`codex/rasputye` и старые `*/task-*` — исторические ветки. Их не переименовывать и не удалять автоматически; оставшуюся активную работу переводить по явному согласованию. Эта таблица не утверждает, что все ветки уже синхронизированы или что люди согласились на назначение.

## Использование

1. Проверить Issues/PR, реестр и чистоту своей рабочей копии. В существующую ветку войти через свой checkout/worktree, не трогать папку коллеги. Если ветка отсутствует, создать её один раз от свежего main и опубликовать; не создавать новый task-branch для очередной задачи.
2. Записать в Issue: направление, ветку, исполнителя/сессию, базовый SHA main, файлы/контракты и зависимости. В одной ветке один активный исполнитель; второй человек может проверять, но не коммитит параллельно без передачи. Несколько Issues не разрешают одновременно писать в одну ветку.
3. Перед новой порцией и финальным review выполнить fetch, затем обычный merge актуального origin/main в ветку. Сохранять чужие изменения, повторить затронутые проверки.
4. Каждый commit должен быть понятной частью конкретной задачи, TASK-ID указывать в сообщении. Один PR из ветки направления в main одновременно. По умолчанию PR — одна завершённая задача; небольшая связанная пачка допустима с перечислением всех Issues/changes и без незавершённых функций. Не держать «всё направление» одним бесконечным PR.
5. На время финального review стабилизировать head: новые несвязанные commits откладываются до merge. Если проверки выявили исправления, добавить их и обновить review затронутой ревизии. Нельзя считать одобренным старый SHA после изменения области/контрактов.
6. После peer review согласованный интегратор объединяет PR обычным merge commit. Затем исполнитель подтягивает main в ту же ветку и начинает следующую порцию. Ветка остаётся; архивируется change, а не ветка.

Для постоянных веток не использовать squash/rebase-and-merge: исходные commits должны сохраняться в общей истории для следующих PR. Почему: [Git FAQ](https://git-scm.com/docs/gitfaq) и [GitHub Docs](https://docs.github.com/en/pull-requests/reference/pull-request-merges#squashing-and-merging-a-long-running-branch).

Если внутри направления постоянно нужны две независимые параллельные линии, согласовать более узкие постоянные направления и обновить реестр. Это изменение распределения работы, а не автоматическое создание ветки на каждый TASK.
