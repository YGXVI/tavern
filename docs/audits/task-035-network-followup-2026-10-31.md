## Что изменилось и что осталось

PR #126 в main: колонка владельца токена, ограничения прав/связей, `patch_token`, `adjust_token`, `move_tokens`, исправления review. Завершённый [recheck d91d84d](https://github.com/YGXVI/tavern/pull/126#issuecomment-6527889777) здесь повторно не проводится. В коде `model.js` сохранение `owner_id: null` уже исправлено; диагностическая проверка ниже подтверждает отсутствие лишних UPDATE токенов.

`sync.js` **побайтно совпадает со срезом `a9c92e6`**. `rg` по `dist/js` не находит вызовов новых трёх RPC. `rpc()` служит общей обёрткой, фактические вызовы из экранов — приглашения/вступление/выбор героя, из очереди — `add_explored`. Поэтому B1 (замена полной строки) и B5 (частичная запись нескольких операций) остаются в клиентском пути. Наличие транзакционных RPC в SQL не означает их использования столом или применения миграции на production.

По коду режим по умолчанию всё ещё sandbox: `SERVER_ENABLED=false`, `?server=1` включает preview. Sandbox использует localStorage и BroadcastChannel одного origin/профиля браузера, другого устройства эти средства не достигают. Серверный preview имеет путь межустройственного обмена через Supabase; физические устройства/живой OAuth этим аудитом не проверены. В [#8](https://github.com/YGXVI/tavern/issues/8#issuecomment-6515518661) автор отдельно сообщил результаты своего стенда и оставшуюся живую проверку. Старые тексты status/glossary и таблицы specs местами описывают прототип; они не отменяют код точного SHA.

## Поток данных

1. `store.commit`: синхронное оптимистичное изменение базы → `backend.afterCommit(before, after)`.
2. `sync.afterCommit`: `explode` двух снимков → `diffRows` по сущностям → `playerCombatOps` для боя игрока → `applyOps` в локальный кэш.
3. Очередь **одного клиента/кампании** → `send` → `sendOne`. UPDATE отправляет **всю `o.row`**, включая JSON `data`; `combats`/`scene_secrets`/`campaign_invites` у мастера — upsert полной строки. Версии/CAS/ID команды нет. Изменённые листы, сцены, рисунки, запросы тоже передаются целой строкой; `add_explored` — исключение с добавлением клеток. Бросок — вставки в log_entries и при необходимости log_secrets, два отдельных запроса.
4. Postgres Changes → `onChange` → `applyChange` → отложенная на 30 мс сборка кампании → `setDB`. Это доставка строк, не журнал с replay/cursor. Новое значение применяется без сравнения ревизии. `loadCampaign` читает таблицы параллельно; первая подписка создаётся **после** чтения, при последующих загрузках события буферизуются.
5. Ошибка сети: повтор **той же операции** (первый запрос + максимум 8 повторов, паузы 700…15000 мс). Успех вставки после потерянного ответа узнаётся по 23505; это не универсальный ключ идемпотентности. Отказ → сообщение/перезагрузка; `whenSynced` ждёт завершения очереди, но её catch поглощает ошибку — resolved не равно подтверждённому сохранению.
6. Realtime reconnect → повторная загрузка только после замеченного DOWN → SUBSCRIBED. `hidden-ids`, drag/select, пинги, presence — отдельные эфемерные события; подтверждения/replay нет. Пропуск скрытия не исправляется до перезагрузки. `removed` убирает канал/кампанию из кэша, но не отменяет уже начатую загрузку/очередь и не вводит поколение доступа. Кэш signed URL карты живёт до ~6 часов и здесь не очищается; это статический вывод, фактический отзыв URL не проверен.

## Приёмка на реальных устройствах — ещё не выполнена

Запуск требует согласованной тестовой кампании и двух самостоятельно вошедших аккаунтов; пароли/токены в отчёт не передавать. Устройства: мастер A и игрок B, разные браузерные профили/сети, серверный preview. Для каждого шага записать SHA клиента, время +05, ID синтетической кампании/действия без персональных записей, ожидаемое/наблюдаемое состояние на обоих клиентах и после reload.

## Минимальный порядок исправлений — предложение, не разрешение реализации
