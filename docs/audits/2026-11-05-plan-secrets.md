# План: тайное мастера вне публичных строк и точечные функции боя (05.11.2026)

Направление: #204 (сервер), находки аудита 04.11. Сверено по `test` `8015dd4`. Подготовил YGXVI / Claude.

## Что сейчас

Уже отделено от игроков: ловушки и закрытые метки (`scene_secrets`), суммы скрытых бросков (`log_secrets`), скрытые токены целиком (`tokens.hidden`, RLS), закрытые снимки существ (`campaign_creatures`).

Ещё **читается любым участником** через API или инструменты разработчика — интерфейс это прячет, база нет:

| Где | Что видно игроку |
|---|---|
| `scenes.data` | все сцены кампании, в том числе неоткрытые: карта, стены, подписи, заметка мастера |
| `scenes.data.walls` | секретные двери и их СЛ |
| `tokens.data` | точные хиты врагов (при «игроки видят только ранения»), настоящее имя за `nameHidden`, пометка «предатель» |
| `combats.data` | скрытые участники боя и их инициатива |

Запись боя и спасбросков: игрок обновляет строку `combats` / `save_requests` целиком, охранники-триггеры сверяют разницу. При одновременных правках клиент перечитывает строку и накладывает свою правку заново.

## Варианты

| | A. Публичная строка + строка секретов (**рекомендую**) | B. Представления с маскировкой полей | C. Оставить, задокументировать |
|---|---|---|---|
| Суть | Тайные поля переезжают в таблицы только для мастера (как уже сделано со сценами и журналом); публичная строка хранит только то, что положено игрокам | Игроки читают через view, которая вырезает поля | «Игра доверия»: тайное защищено интерфейсом |
| Реальное время | работает (postgres_changes с RLS по таблице) | **не работает**: Realtime не шлёт изменения представлений | как сейчас |
| Защита | на уровне базы | на уровне базы, но ломает синхронизацию | нет |
| Объём | ~1–1,5 недели | — | 0 |

## Рекомендуемый вариант A — этапы

1. **Сцены.** Колонка `scenes.revealed` (мастер открывает сцену); RLS: игрок читает только открытые сцены и сцену, где стоит его токен. Заметка мастера и секретные двери с СЛ — в `scene_secrets.data`; в публичных `walls` секретная дверь до обнаружения выглядит обычной стеной, после — дверью. Охранник `guard_scene_update` не меняется.
2. **Токены.** Таблица `token_secrets(token_id, campaign_id, data)`, только мастер. Туда: точные хиты и макс. хиты врагов (кроме героев, своих токенов и призывов игроков и режима «игроки видят точные хиты»), настоящее имя при `nameHidden`, «предатель», заметки. Публичная строка получает показываемое имя и уровень ранения (`wound`); его пересчитывает триггер при изменении секрета, поэтому ранение у игроков обновляется в реальном времени. `adjust_token_once` по врагу меняет секрет, ответ мастеру — прежний.
3. **Бой.** Скрытые участники — в `combat_secrets` (мастер), в публичном порядке их нет до раскрытия. Точечные функции вместо записи строки игроком:
   - `combat_player(campaign, op, operationId)` — свой бросок инициативы, конец своего хода, «Отход», ничья — с проверкой «это мой участник»;
   - `save_result(request, token, result, operationId)` — результат своего спасброска.
   После перехода у игроков отзывается `UPDATE` на `combats` и `save_requests`; охранники остаются второй линией.
4. **Клиент.** `model.js` раскладывает поля по публичной строке и секрету (как уже раскладывает сцены и журнал); `sync.js` подписывается на новые таблицы секретов только у мастера; бой и спасбросок игрока — вызовами функций с ключом повтора вместо перечитывания строки.
5. **Перенос данных** — одной миграцией: поля выносятся из `data` в секреты. Для живой базы это меняет формат хранимых данных, поэтому — только после бэкапа с проверкой восстановления и в одном выпуске с клиентом (старый клиент новых полей не знает).
6. **Проверки.** `rls.sql`: игрок не читает неоткрытую сцену, СЛ двери, точные хиты, настоящее имя, скрытых участников; не обновляет `combats` напрямую; функции отвергают чужого участника; повтор по `operationId`. Приёмка `tools/stand-acceptance.mjs` расширяется этими сценариями. Браузер: стол мастера и игрока на стенде.

Порядок: 3 (бой) можно делать первым — он независим и сразу снимает перечитывание при конфликтах; затем 2, 1, перенос данных.

Откат: обратная миграция возвращает поля в `data` (секретные таблицы сохраняются до подтверждения).

**Решение, которое нужно:** утвердить вариант A — изменение модели безопасности (новые таблицы секретов, закрытие прямой записи игроком в бой и спасброски, перенос полей на живой базе после бэкапа).
