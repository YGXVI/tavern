# План P4b — серверная проверка сборки героя (05.11.2026)

Направление: #202 (лист и правила), связано с #200 (конструктор). Сверено по `test` `8015dd4`. Подготовил YGXVI / Claude.

## Что сейчас

- `create_character_sheet` (P4a) и `level_up_character` проверяют форму блока `creation`, известные классы SRD, уровни и хиты по формуле. Выборы внутри сборки (характеристики, навыки, заклинания, черты, варианты и их предпосылки) сервер **не проверяет**: ставит `creation.verified = 'client'`.
- Вся логика правил — в `dist/js/rules/character-builder.js` (`evaluateBuild`, 650 строк) на справочниках `dist/js/data/*-2014.json` (~0,9 МБ). Тот же код работает в браузере.
- Политика кампании (разрешённые источники, способ характеристик, черты, мультикласс) пока живёт только у клиента; `policyRevision` и `rulesRevision` лишь записываются.

Чем это грозит: игрок, правящий запросы руками, может создать героя с недопустимыми выборами. Мастер это увидит на листе, но сервер не остановит.

Почему не PL/v8 (JS внутри Postgres): в Supabase на Postgres 17 расширение `plv8` снято с поддержки.

## Рекомендуемый вариант A — как устроено

1. **Политика кампании** — `campaigns.data.creationPolicy` (источники, способы характеристик, черты, мультикласс, гибкие бонусы расы). Пишет только мастер (действующая политика `campaigns_update`); `policyRevision` = хэш политики, считает сервер.
2. **Реестр ревизий справочника** — таблица `rules_revisions(revision, created_at)`, заполняется миграцией вместе с выкаткой. Сборка с неизвестной ревизией получает `stale_rules`.
3. **Edge Function `validate-build`** (Deno, код из `dist/js/rules/**` и справочники в сборке функции):
   - вызывается с JWT игрока, без service role; кампанию и политику читает под RLS игрока;
   - выполняет `evaluateBuild` и `toCharacterData`, сверяет с присланными `creation` и листом;
   - при успехе возвращает подпись HMAC-SHA256 от `(campaignId, characterId, operationId, sha256(payload), policyRevision, rulesRevision)` со сроком 10 минут; при ошибке — коды движка (`ability_cap`, `stale_policy` …);
   - в базу не пишет.
4. **SQL-команды** `create_character_sheet` и `level_up_character` получают необязательный `p_attestation`. Подпись сверяется ключом из Supabase Vault (`pgcrypto` `hmac`); верная — `verified = 'server'`, отсутствует — прежнее `'client'` (переходный период), неверная или просроченная — `22023`. Флаг кампании `creationPolicy.requireServerCheck` позволяет мастеру запретить непроверенные сборки.
5. **Клиент**: окно конструктора сначала вызывает `validate-build`, затем команду с подписью; повтор после потери ответа идёт с той же подписью (идемпотентность по `operationId` прежняя). Пометка на листе — «проверено сервером» / «проверено в браузере».
6. **Проверки**: общие фикстуры `tests/character-builder.test.js` гоняются и в Node, и в `deno test` функции; в `rls.sql` и `local_pg.py` — верная, чужая, просроченная и подделанная подпись; поддельный прямой запрос при `requireServerCheck` отклоняется. CI выкатывает функцию на тестовый проект вместе с миграциями.

Что потребуется от тебя: решение «да, A»; затем один раз создать секрет подписи в тестовом проекте (Edge Function Secrets и Vault — пошаговую инструкцию дам, значение в чат не передаётся) и добавить токен доступа Supabase в секреты GitHub для выкатки функции на стенд. На живой базе — после бэкапа, вместе с выпуском.

Откат: удалить функцию и параметр подписи новой миграцией; созданные герои остаются, их пометка `verified` не меняется.

**Решение, которое нужно:** утвердить вариант A — допустить Edge Function как второй серверный компонент (это меняет пункт D6 r1 «Edge-платформа не предлагается»).
